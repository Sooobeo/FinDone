# FinDone 실무면접 자료집 설계서

대상 경험: Finance Learning App and Quiz Option Ranking Model, 2026년 7~8월  
문서 성격: 원자료 검증·추가 조사·교재 제작 계획  
현재 상태: 제출 이력서 1쪽만 확인. 코드·데이터·실험·검토 기록은 미확보. 아래 검증은 아직 수행하지 않았다.

## 1. 자료집이 해결해야 할 질문

**금융 퀴즈의 오답 후보를 어떻게 정의·생성·순위화했고, 품질과 실험 결과를 어떻게 검증했는가?**

공고의 Python 분석, 분석 기준 설계, 결과 해석·검증에 연결한다. 독립 프로젝트라는 사실을 유지하면서 AI·외부 라이브러리의 지원과 본인의 설계·구현·검토 범위를 구분한다.

## 2. 이력서 기재 사실

- 개인 Android 앱과 콘텐츠 관리 웹사이트를 만들고, 135개 금융 개념의 설명·공식·출처를 퀴즈·복습 기록과 연결했다.
- 개념 검색에 SQLite FTS5/BM25를 사용했다.
- 18개 특성의 Python XGBoost 랭킹 모델을 학습해 다른 개념 설명에서 그럴듯한 오답 후보를 선택했다.
- 키워드 및 사전학습 임베딩 검색 설정 198개를 비교했다.
- 개념을 95/20/20으로 나눠 학습·검증·테스트에 사용하고 검증 데이터로 설정을 선택했다.
- 자동 생성 관련성 라벨, 실험 설정, 비교 결과를 문서화했다.
- 405개 문제은행을 구성하고 콘텐츠 제작 시 후보 순위화를 활용했다. 자동 검사와 수동 검토로 정답 노출·중복 선택지·개념 불일치를 점검하고 변경 후 재승인을 요구했다.

최종 성능, 특성 목록, 실제 모델 목적함수, 라벨 규칙, 검사 통과율, 사용 규모는 이력서만으로 확인할 수 없다.

## 3. 주장별 검증 계획

| ID·우선순위 | 검증할 내용 | 확보할 근거 | 검증 방법·판정 기준 |
|---|---|---|---|
| F01·P0 | 135개 개념·405개 문제의 의미 | 콘텐츠 파일·DB·내보내기 | 고유 ID, 버전, 활성·초안·승인 상태별 수를 세어 생성·검토·제공 수를 구분한다. 단순히 135×3으로 의미를 추정하지 않는다. |
| F02·P0 | 검색과 랭킹의 실제 사용 흐름 | 검색·학습·추론 코드, 앱·관리 웹 호출 경로 | 개념 검색과 퀴즈 후보 생성의 관계를 추적한다. BM25·임베딩·모델 중 실험용과 최종 채택 구성을 분리한다. |
| F03·P0 | 18개 특성과 학습 행·그룹 | 특성 코드·열 목록·학습 파일 | 한 행이 무엇인지, 후보 그룹과 라벨을 어떻게 연결하는지 확인한다. 대표 입력 하나로 특성 3개를 재계산하고 예측 시점 가용성을 점검한다. |
| F04·P0 | 자동 라벨의 정의와 신뢰성 | 라벨 생성 코드·규칙·수동 검토 | 생성 기준, 허용 값, 라벨 오류·모호 사례를 확인한다. 라벨 규칙과 특성·평가 규칙의 중복으로 자기 기준만 잘 맞추는 구조인지 점검한다. |
| F05·P0 | 95/20/20 분할과 누수 | 개념 ID 목록·분할 코드·후보 풀 | 개념 집합의 중복, 파생 문제의 소속, 학습 통계 사용 범위를 확인한다. 후보로 등장하는 개념이 분할을 넘는 경우 실제 사용 목표를 기준으로 해석한다. 등장 자체만으로 누수라고 단정하지 않는다. |
| F06·P0 | 198개 설정 비교와 최종 선택 | 설정 목록·실험 로그·선택 코드 | 설정 ID와 조합 수, 성공·실패 실험, 선택 지표, 검증·테스트 접근 순서를 대조한다. 198개를 전부 XGBoost 튜닝이라고 바꿔 말하지 않는다. |
| F07·P0 | 실제 성능·비교의 공정성 | 평가 코드·기본 방법·결과표 | 지표의 집계 단위와 후보 조건을 확인한다. 동일 평가 입력으로 기본 방법과 최종 방법의 저장 결과를 재계산하고 차이를 보고한다. |
| F08·P1 | 테스트·검증의 불확실성 | 실험 타임라인·반복 기록 | 테스트를 보고 변경했는지 확인한다. 검증 개념 수와 많은 설정 비교의 한계를 정리한다. 추가 검증은 당시 결과와 별도 표기한다. |
| F09·P0 | 자동 검사·수동 검토·재승인 | 검사 코드·상태 전이·검토 기록 | 정답 노출·중복·개념 불일치의 정의를 확인한다. 대표 정상·오류·변경 사례로 검사와 승인 상태의 동작을 추적한다. |
| F10·P1 | 모델이 실제로 기여한 지점 | 콘텐츠 생성·배포 흐름·사용 기록 | 콘텐츠 제작 단계의 후보 순위화와 앱 실행 중 실시간 추론을 구분한다. 사용자 효과나 상용 운영 성과는 별도 근거가 있을 때만 기재한다. |

검증마다 상태는 `미확인 / 원자료 확인 / 재현 확인` 중 하나로 기록하고, 원래 결과와 재현 결과가 다르면 원인을 남긴다.

## 4. 더 찾아야 할 자료와 본인 확인 질문

### 먼저 찾을 원자료

1. 앱·관리 웹·분석 코드 저장소와 당시 버전, 실행 설명, 의존성 목록
2. 금융 개념·문제·출처 데이터와 DB 구조
3. 18개 특성 목록, 관련성 라벨 생성 규칙, 학습 그룹 정의
4. 95/20/20 개념 ID 목록, 검색 후보 범위 설정
5. 198개 설정 목록, 기본 방법·최종 방법의 실험 결과와 평가 코드
6. 콘텐츠 검사·승인 기록, 실패 사례, 발표·프로젝트 문서

### 기록만으로 판단하기 어려운 사항

- 처음의 불편이나 문제는 무엇이었고, 실제로 어떤 대안을 비교했는가?
- 왜 그럴듯한 오답을 이 방법으로 정의했는가? 학습 효과를 직접 평가한 적이 있는가?
- 가장 어려웠던 오류 하나와 본인이 바꾼 결정은 무엇인가?
- 생성형 AI가 작성·제안한 부분과 본인이 확인·수정한 부분은 무엇인가?

## 5. 보충 학습·조사 범위

| 학습 주제 | 자료집에서 설명할 수준 | 조사·확인 출처 |
|---|---|---|
| 검색과 랭킹 | 후보를 찾는 단계와 순서를 정하는 단계, 키워드·의미 검색의 차이 | 실제 검색 코드 + SQLite FTS5 공식 문서 + 실제 임베딩 모델 문서 |
| BM25·임베딩 | 대표 질의와 후보로 점수가 어떤 의미인지 설명. 실제 구현의 점수 방향·정렬도 확인 | https://www.sqlite.org/fts5.html 및 사용 모델의 모델 카드 |
| XGBoost 랭킹 | 특성·라벨·질의 그룹·목적함수·추론 점수를 실제 사용 설정에 맞춰 설명 | https://xgboost.readthedocs.io/en/stable/tutorials/learning_to_rank.html |
| 랭킹 평가 | 실제 사용 지표부터 설명하고 필요할 때 NDCG·MRR·Precision@k 등과 비교 | 실제 평가 코드 + 지표 공식 문서 |
| 분할·데이터 누수 | 개념·파생 문제·후보·전처리·라벨의 경계와 실제 사용 시점 | https://scikit-learn.org/stable/common_pitfalls.html |
| 품질 검증·변경 관리 | 검사 규칙, 수동 검토 이유, 승인 상태, 변경 후 재검증 | 실제 검증·관리 웹 코드와 기록 |

공식 문서는 자료집 제작 시 읽고 프로젝트 버전과 맞는지 확인한다. 이 링크 목록은 실제로 사용한 라이브러리 설정을 증명하지 않는다. 고급 수식 유도나 다른 모델 구현은 핵심 설명에 필요할 때만 추가한다.

## 6. 최종 자료집 구성안

| 장 | 설명할 내용 | 만들어야 할 학습 자료 |
|---|---|---|
| 1. 서비스와 문제 | 누가 무엇 때문에 사용하는지, 콘텐츠 제작과 앱 사용 흐름 | 입력·처리·출력 그림, 30초 설명 |
| 2. 실제 데이터 | 개념·문제·후보·특성·라벨·그룹의 관계 | 실제 예시 표와 용어 설명 |
| 3. 검색에서 랭킹까지 | BM25·임베딩·XGBoost의 역할과 선택 이유 | 동일 질문의 후보 변화와 코드 해설 |
| 4. 실험을 믿을 근거 | 분할, 누수, 라벨, 기본 방법, 지표, 198개 비교 | 분할 지도, 검증 결과표, 재현 기록 |
| 5. 콘텐츠 품질 | 자동 검사의 경계와 수동 검토·재승인 | 정상·오류·수정 후 사례와 상태 변화 |
| 6. 면접 답변 | 선택·기여·검증·한계·직무 연결 | 2분 설명, 단계별 꼬리질문, 복습 카드 |

각 장은 개념을 먼저 풀고 실제 구현으로 연결한다. 지표나 실패 사례가 없으면 예시를 새로 만들 수 있지만 반드시 `학습용 예시`로 표시한다.

## 7. 검증 후 만들 연습문제

- P0: 한 문제를 골라 입력·후보·특성·라벨·순위·검토를 순서대로 설명하기
- P0: 학습·검증·테스트에 넣어도 되는 정보와 넣으면 안 되는 정보를 이유와 함께 분류하기
- P0: 기본 방법과 최종 모델의 실제 결과를 읽고 장점과 한계를 말하기
- P1: 자동 라벨이 틀린 사례를 보고 성능 해석에 미치는 영향을 설명하기
- P1: 내용 수정 뒤 승인 상태가 어떻게 바뀌어야 하는지 실제 구현과 비교하기

복습 답안에는 근거 ID를 연결한다. 아직 확보하지 못한 성능 수치는 만들어 넣지 않는다.

## 9. 완료 기준과 범위 제한

- [ ] 이력서의 숫자 135·405·18·198·95/20/20의 의미와 근거가 정리됨
- [ ] 실제 데이터 한 건으로 전체 처리 과정을 따라갈 수 있음
- [ ] 기본 방법·지표·최종 결과·검증 한계를 구분해 설명함
- [ ] 자동 라벨·분할·후보 범위의 쟁점을 실제 구현으로 설명함
- [ ] 실패·수정·재검증 사례 하나를 확보하거나 미확인으로 명시함
- [ ] 30초·2분 답변에 검증되지 않은 성과가 없음

자료집 작성을 이유로 앱 기능을 추가하거나 198개 실험을 전부 다시 실행하는 것은 기본 범위가 아니다. 핵심 결과 확인에 필요한 경우에만 제한적으로 재현한다.
