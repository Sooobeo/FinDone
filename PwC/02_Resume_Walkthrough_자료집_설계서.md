## 1. 목적과 이번 설계의 기준

FinDone에 관해 이력서에 쓴 네 개 bullet을 본인의 말로 설명하고, 면접관이 어느 문장에서 질문하더라도 실제 데이터·구현·판단·결과로 이어서 답할 수 있는 학습 자료집을 만든다. 준비 기한이나 분량 제한을 이유로 학습·근거 확인 범위를 줄이지 않는다. 답변의 길이는 대화 상황에 맞추되, 자료집 자체에는 설명에 필요한 깊이를 확보한다.

대상은 FinDone 경험 하나다. `00` 안내가 정한 경험별 독립 자료집 방식에 따른다. YCC와 Financial Academy는 제외한다. 전체 이력서 자기소개, 다른 프로젝트의 상세 해설, 독립적인 기업 업무 케이스, 임원면접 종합 준비는 포함하지 않는다. 학력·언어·일반 도구는 FinDone 설명에 실제로 필요한 경우만 연결한다.

기존 `01_FinDone_자료집_설계서.md`의 F01~F10을 유지하고 `00`의 근거 표시·공통 편집 형식으로 확장한다. 본문 순서는 이력서 네 bullet에 맞추되 각 장 안에서는 개념부터 배우고 적용·판단·검증으로 이어지게 한다. 면접 답변은 학습 내용을 토대로 장 끝과 마지막 연습 장에 둔다.

### 확인한 자료와 현재 상태

- `Kyuri_Moon_Resume_ (1).pdf`: 제출 이력서 1쪽 전체를 읽고 시각적으로 확인했다.
- `PwC공고.pdf`: 제공된 PDF 2쪽 전체를 읽고 시각적으로 확인했다. 인쇄물의 바닥글에는 1/4, 2/4가 표시되지만 파일에 포함된 페이지는 2쪽이다.
- `01_FinDone_자료집_설계서.md`: 기존 설계서 전체를 확인했다.
- `00_자료집_설계_안내.md`: 전체를 확인했고 이번 최종 설계에 반영했다. 이 문서가 말하는 원자료 미확보는 작성 당시 폴더 기준이다. 현재 저장소에서는 아래 코드·데이터·실험 기록을 발견하고 일부를 읽었다.
- `tools/train_concept_question_model.py`: 분할, 문항 구성, 특성, 약지도 라벨, 검색, 학습·평가 함수의 구현을 확인했다. 전체 파이프라인 실행이나 결과 재계산은 하지 않았다.
- `content/model/concept-model-config.json`, `concept-split.json`, `concept-question-bank.generated.json`: 설정 일부, JSON 구조·메타데이터와 실제 문제 한 건을 확인했다. 전체 고유 ID·검토 상태별 집계는 아직이다.
- `docs/modeling/README.md`와 `experiments/cmq-v2-20260816-014214-89cf4e66.md`: v2.2와 v3의 구분, 저장된 결과와 한계 설명을 확인했다. 전체 198행의 독립 재계산이나 당시 실행 절차 감사는 아직이다.
- `build/concept-model/`에 중간 JSONL과 모델 파일이 존재한다. 파일 존재만 확인한 자료는 입력 일치·내용·재현성을 검증한 것으로 표시하지 않는다. Owner 결정 기록도 존재를 확인했으나 본인 기여와 실제 검토 범위는 추가 확인이 필요하다.
- 공고에 명시된 전형은 서류심사 → 실무면접 → 임원면접이다. Resume walkthrough 준비 방식은 사용자가 지정했다. 아래 예상 질문과 평가 관점은 준비를 위한 해석이며 PwC의 실제 질문 목록을 확보한 것은 아니다.

## 2. 공고를 반영한 준비 관점

공고는 기업 시스템 및 업무 데이터의 추출·전처리·분석, 리스크·이상징후 분석 로직과 기준 설계 지원, 결과 시각화·보고서·산출물 작성을 담당 업무로 제시한다. SQL·Python 활용과 전처리·결과 해석을 지원 자격으로 명시한다.

| 공고의 업무 | FinDone에서 설명할 경험 | 반드시 확인할 경계 |
|---|---|---|
| 데이터 추출·전처리·분석 | 개념·문제·출처 데이터 구조, 후보 데이터 구성, 특성 산출, Python 분석 흐름 | SQLite 사용만으로 복잡한 SQL 분석 경험을 추정하지 않는다. 실제 작성한 쿼리와 처리 코드를 확인한다. |
| 분석 로직·기준 설계 | 그럴듯한 오답의 정의, 관련성 라벨, 후보 제외·검사 규칙 | 실제로 정한 기준과 도구가 제공한 기본 동작을 구분한다. |
| 결과 해석 | 비교 기준, 검증·테스트 분리, 최종 결과와 한계 | 자동 라벨 기준 성능과 사람에게 유용한 오답 품질을 구분한다. |
| 산출물 작성 | 설정·비교 결과 문서, 출처 연결, 검토·승인 기록 | 존재하는 기록과 앞으로 작성할 학습 자료를 구분한다. |

FinDone에서 기업 리스크 탐지를 수행했다고 표현하지 않는다. 데이터의 단위를 정하고, 판단 기준을 구현하고, 결과를 검증·설명한 경험이 공고의 업무에 어떻게 이어지는지 설명한다. 금융 앱이라는 주제만으로 직무 연관성을 대신하지 않는다.

## 3. 경험별 자료집 안에서의 범위

`00`은 공시 Q&A, FinDone, HappyLLM, ETF의 독립 자료집을 정의한다. 이번 파일은 그중 FinDone을 구체화한다. 권장 제작 순서는 전체 자료집 관리상의 안내이며, 이미 요청받은 FinDone 작업을 다른 경험 자료가 올 때까지 미루는 조건으로 사용하지 않는다.

현재 `PwC` 폴더에는 `00`에서 참조하는 공시·HappyLLM·ETF 설계서가 없다. `C:/PwC 면접대비/` 링크는 원본 안내의 경로이며 현재 저장소 경로로 간주하지 않는다. 누락된 다른 경험의 설계서를 새로 만들거나 내용을 추정하지 않는다. 기존 `02_Resume_Walkthrough_자료집_설계서.md`는 이 폴더에서 사용하는 FinDone 최종 설계 파일이다.

도입에서는 FinDone의 목적·기간·역할·입력·처리·출력과 네 bullet의 관계만 안내한다. 공고와의 연결은 실제 데이터 처리, 기준 설계, 검증, 결과 보고로 설명한다. 이력서에 없는 BI·ERP·산업 경험을 덧붙이지 않는다.

## 5. 네 개 bullet의 정확한 출발점

다음 영문은 제출 이력서의 FinDone 항목이다. PDF 추출 과정에서 생기는 줄바꿈만 정리했다. 자료집에서 각 원문과 한국어 의미를 함께 제시한다.

### B1. 서비스·데이터·개념 검색

> Built a personal Android app and content management website linking explanations, formulas and sources for 135 finance concepts with quizzes and review records; implemented concept search with SQLite FTS5/BM25.

- 첫 답변: 누구를 위한 서비스이며 개념·문제·복습 기록을 어떻게 연결했는지 설명한다.
- 심화: 개념 한 건의 ID·설명·공식·출처와 연결 관계, 실제 검색 입력·결과, SQL과 Python이 각각 쓰인 지점.
- 선택 이유: 해당 저장·검색 방식을 선택한 당시 이유와 실제 검토한 대안. 사후에 떠올린 대안은 구분한다.
- 주의: 앱의 개념 검색과 콘텐츠 제작의 후보 검색을 같은 경로로 가정하지 않는다.
- 근거: F01·F02·F10.

### B2. 랭킹 모델·검색 설정 비교

> Trained an 18-feature XGBoost ranking model in Python to select plausible incorrect quiz choices from other concept descriptions; compared 198 keyword and pretrained embedding retrieval configurations.

- 첫 답변: 어떤 입력에서 어떤 후보를 골라 어떤 순서를 만드는 모델인지 설명한다.
- 심화: 한 학습 행, 한 그룹, 라벨과 특성의 차이, 18개 전체 목록과 대표 특성 계산, 실제 목적함수·추론 점수, 검색 설정 조합.
- 선택 이유: 왜 단순 검색·규칙만으로 충분하지 않았는지 실제 비교 결과와 당시 기록으로 설명한다. 결과가 이를 뒷받침하지 않으면 그 한계를 밝힌다.
- 주의: 198개를 XGBoost 하이퍼파라미터 조합 수로 바꾸지 않는다. 순위 점수를 정답 확률로 해석하지 않는다.
- 근거: F02·F03·F04·F06·F07.

### B3. 분할·평가·문서화

> Separated 95/20/20 concepts for training/validation/testing; selected configurations using validation data, evaluated on test data, and documented automatically generated relevance labels, experimental settings and comparative results.

- 첫 답변: 무엇을 나누었고 검증 데이터와 테스트 데이터를 각각 어디에 썼는지 설명한다.
- 심화: 개념·문제·후보의 분할 지도, 학습 통계의 범위, 자동 라벨 규칙, 평가 지표 계산, 동일 조건의 기본 방법 비교, 설정 선택과 테스트 접근 순서.
- 해석: 실제 수치가 측정하는 대상, 일반화의 범위, 작은 검증 집합과 여러 설정 비교, 자동 라벨과 특성·평가 규칙 중복의 영향.
- 주의: 이력서는 테스트 평가를 수행했다고 명시하지만 그 독립성이나 성능 수준까지 입증하지 않는다. 현재 코드만으로 당시 실험 절차를 확정하지 않는다.
- 근거: F04·F05·F06·F07·F08.

### B4. 콘텐츠 제작·검사·재승인

> Assembled a 405-question bank and ranked candidates during content production; combined automated checks with manual review for answer leakage, duplicate choices and concept mismatches, and required renewed approval after content changes.

- 첫 답변: 후보 순위화가 콘텐츠 제작 단계에서 어떻게 사용되고 사람이 어디서 판단했는지 설명한다.
- 심화: 문제은행 상태별 수량, 검사 규칙과 탐지하지 못하는 경우, 실제 검토 기록, 수정 전후 승인 상태와 배포 반영 경로.
- 사례: 정상 → 오류 발견 → 수정 → 재검증 → 재승인의 실제 기록을 연결한다. 기록이 없으면 구현으로 확인 가능한 상태 전이와 실제 발생 사례를 구분한다.
- 주의: 문제은행 구성 수와 승인·배포 수, 검사 기능의 존재와 실제 수동 검토 수행을 구분한다. 앱에서 실시간 추론했다고 바꾸어 설명하지 않는다.
- 근거: F01·F09·F10.

## 6. 각 장의 작성 형식과 설명 깊이

모든 장은 `학습 목표 → 필요한 개념 → 나의 실제 적용 → 판단·검증 → 확인 문제`를 공통 골격으로 사용한다. 도입·근거 지도·연습 장에도 해당 장의 목적에 맞춰 이 골격을 적용한다.

1. **학습 목표:** 연결된 bullet·검증 ID와 읽고 나서 설명할 수 있어야 하는 질문을 적는다.
2. **필요한 개념:** 처음 등장하는 용어에 한국어 뜻과 작은 예시를 붙인다. 일반 SQL·통계도 실제 처리에 필요한 범위로 설명한다.
3. **나의 실제 적용:** 이력서 원문을 실제 입력·출력·데이터·코드에 연결한다. 코드가 하는 일과 본인이 직접 한 일을 구분한다.
4. **판단·검증:** 당시 선택 이유와 대안, 확인 방법, 결과, 실패·예외, 한계를 설명한다. 현재의 개선안은 별도 표시한다.
5. **확인 문제:** 계산·표 해석·오류 찾기·판단 설명 문제와 답안을 두고, 장 끝에 짧은 구어체 답변과 꼬리질문을 정리한다.

학습 본문을 읽은 뒤 장 끝의 답변으로 복습하고 부록에서 근거를 확인할 수 있게 내부 링크를 둔다. 30초·2분 답변은 마지막 연습 장에 모은다. 모든 근거가 확보되기 전에도 확인된 부분과 개념 설명은 집필하되 미확인 경험을 채워 넣지 않는다.

### 학습 중요도

| 표시 | 의미 | FinDone 적용 |
|---|---|---|
| P0 | 반드시 설명할 핵심 | 네 bullet, 다섯 핵심 숫자, 입력·출력, 본인 역할, 라벨·분할·성능의 의미, 품질 검토 |

## 7. 공통 실제 사례와 산출물

실제 문제 한 건을 골라 개념 데이터 → 후보 자격 판정 → 검색·특성·라벨 → 학습과 추론 → 선택지 → 검사·검토를 추적한다. 라벨은 학습·평가에 쓰이고 추론 때 입력으로 요구되는 값이 아님을 그림에서 분리한다. 하나의 사례로 설명할 수 없는 예외는 별도 사례로 보충한다.

필수 학습 자료는 다음과 같다.

- 앱 사용 흐름과 콘텐츠 제작 흐름을 구분한 전체 구조도.
- 실제 개념·문제·후보·학습 행·그룹의 관계표.
- 18개 특성 전체표와 대표 3개 특성의 계산 예시.
- 198개 설정의 구성·성공 여부·선택 기준 요약표.
- 개념 분할 및 후보 풀 지도와 정보 사용 시점 설명.
- 기본 방법·최종 방법의 동일 조건 결과표와 지표 계산 예시.
- 검사 정상·오류·변경 사례 및 검토·승인 상태표.
- 본인 결정과 기여를 정리한 사례 카드.

학습용으로 만든 수치·오류 사례는 명시적으로 표시하고 실제 경험 답변의 근거로 사용하지 않는다. 대표 실제 사례를 확보하지 못하면 해당 경로의 미확인 부분을 남긴다.

## 8. 본인 기여와 확인 질문

코드의 존재만으로 본인이 직접 작성한 범위나 당시의 판단 이유를 확정할 수 없다. 다음 질문은 근거 조사 중 필요한 항목을 모아 확인한다.

- 처음 해결하려던 불편과 목표 사용자는 누구였는가?
- 당시 본인이 비교하고 선택한 대안은 무엇이며 결정 이유는 무엇인가?
- AI가 제안·작성한 부분, 직접 설계·수정·검증한 부분은 각각 무엇인가?
- 가장 어려웠던 실제 오류는 무엇이고 본인이 어떤 조치를 했는가?
- 수동 검토를 누가 어떤 기준으로 어느 범위까지 수행했는가?
- 실제 사용·배포 범위와 확인한 효과는 무엇인가?

독립 프로젝트라는 사실은 유지한다. 기여 설명은 설계·구현·분석·검토 각각의 범위와 사례로 작성한다. 다른 팀 프로젝트의 운영 경험을 FinDone의 협업 경험으로 옮기지 않는다.

## 9. 검증과 집필 순서

1. 이력서 네 문장을 주장 단위로 나누어 B1~B4와 F01~F10에 연결한다.
2. 저장소의 코드·데이터·설정·실험·검토 기록을 찾고 당시 버전을 식별한다. 현재 상태와 이력서 대상 시기의 차이를 기록한다.
3. 실제 데이터 관계와 전체 처리 흐름을 확인하고 공통 사례를 선정한다.
4. 수량·특성·설정 비교·분할·평가·승인 동작을 확인한다. 필요한 핵심 결과를 제한적으로 재현한다. 전체 실험 재실행은 설명에 필요한 근거가 부족할 때 범위를 결정한다.
5. 기술 개념과 코드 해설, 결과 해석을 집필한다. 당시 결과와 새 재현 결과를 분리한다.
6. 기록으로 알 수 없는 동기·기여·결정 이유를 본인에게 확인한다.
7. 확인된 내용으로 핵심 답변과 꼬리질문 답변을 작성하고 직무 연결을 정리한다.
8. 원문·답변·표·부록의 숫자와 주장 범위를 대조한다.

기한에 따른 축약이나 일별 일정은 두지 않는다. 실제 결과에 영향을 주는 불확실성을 해결할 필요에 따라 조사 깊이를 정한다. 자료집 제작을 위해 앱 기능이나 모델을 개선하면 당시 경험과 섞일 수 있으므로 기능 추가는 이 작업의 범위에 넣지 않는다.

### 근거 표시와 기록 형식

`00`의 여섯 표시를 그대로 사용한다. 서로 다른 종류의 근거가 하나의 주장에 함께 붙을 수 있으며, 여섯 표시를 단순한 완료 단계로 취급하지 않는다.

| 표시 | 자료집에서의 사용 |
|---|---|
| 이력서 기재 | 제출 원문에서 확인한 주장. 실제 수행 검증과 구분 |
| 원자료 확인 | 코드·데이터·기록에서 확인한 범위. 파일·행·버전·확인 날짜 기록 |
| 재현 확인 | 입력·설정·실행 방법·결과·기존 결과와의 차이를 함께 기록 |
| 본인 설명 | 당시 판단·역할의 진술. 기록으로 확인된 부분과 기억을 구분 |
| 미확인 | 확인할 내용과 필요한 자료를 명시 |
| 추가 학습·실습 | 면접 준비 중 만든 예시·실습·새 개선안. 당시 수행 사실과 분리 |

주장별 근거표는 `주장 ID / 주장 / 근거 ID / 검증 방법 / 확인 결과 / 상태 / 답변에 사용할 표현 / 남은 확인`으로 통일한다. F01~F10 아래에 필요하면 세부 주장 ID를 추가하고 B1~B4와 연결한다.

별도 자료 목록은 `근거 ID / 파일·행 또는 페이지 / 버전·시점 / 확인 날짜 / 확인 범위`로 만든다. 파일·기록이 있다는 사실과 그 기록이 주장하는 내용의 정확성을 구분한다. 공개 문서는 개념 설명에만 사용하며 개인 성과의 증거로 사용하지 않는다.

외부에 보여줄 코드·화면·표에는 면접 설명에 불필요한 연락처·계정·API 키·타인 대화를 포함하지 않는다. 원본을 바꾸지 않고 자료집의 발췌 범위를 조정한다.
