## 1. 이번에 만든 문서의 목적

이 문서들은 향후 경험별 교재·자료집을 제작하기 위한 설계서다. 무엇을 더 찾아야 하는지, 어떤 주장을 어떻게 검증할지, 검증한 내용을 어떤 순서로 공부할 수 있게 만들지를 정의한다. 최종 자료집이나 완성된 면접 답변은 아직 작성하지 않았다.

현재 작업 폴더에서 확인한 원자료는 `Kyuri_Moon_Resume_ (1).pdf` 1쪽과 `PwC공고.pdf` 1~2쪽이다. 프로젝트 소스코드·데이터·실험 결과·발표자료·활동 기록은 현재 폴더에서 확보하지 못했다. 따라서 **이력서에 기재됐다는 사실과 실제 수행·성과가 독립적으로 검증됐다는 사실을 구분**해야 한다.

이력서의 프로젝트 4개를 각각 독립적인 설계서로 나눴다. 사용자의 요청에 따라 YCC와 Financial Academy는 제외했다. 학력·언어·일반 도구 숙련도는 필요한 범위에서 개별 프로젝트와 공통 점검 항목에 연결한다.

## 3. 모든 자료집에 적용할 근거 표시

| 표시 | 의미 | 작성 방식 |
|---|---|---|
| 이력서 기재 | 제출 문서에서 확인한 주장 | 원문 위치와 표현을 기록하되 실증 완료로 표시하지 않는다. |
| 원자료 확인 | 코드·데이터·기록으로 확인한 내용 | 근거 파일·행·버전·확인 날짜와 확인 범위를 남긴다. |
| 재현 확인 | 확보한 자료로 결과를 다시 확인한 내용 | 입력·설정·실행 방법·결과·기존 결과와의 차이를 남긴다. |
| 본인 설명 | 당시 판단·역할 등에 관한 본인 진술 | 기록으로 확인된 부분과 기억에 의존하는 부분을 구분한다. |
| 미확인 | 근거를 아직 확보하지 못한 내용 | 어떤 자료가 있어야 확인 가능한지 명시한다. |
| 추가 학습·실습 | 면접 준비 과정에서 새로 배우거나 수행한 내용 | 당시 수행 사실에 섞지 않고 별도 표시한다. |

코드가 존재한다는 사실만으로 운영 중 실행됐다고 판단하지 않는다. 문서화된 규칙과 실제 코드에 반영된 규칙도 구분한다. 공개 자료는 개념·방법을 설명하는 근거로 쓰며, 개인 프로젝트의 실제 성과를 증명하는 근거로 사용하지 않는다.

## 4. 공통 제작 절차

1. **자료 목록 작성:** 각 설계서의 요청 목록을 기준으로 원자료를 모으고 자료 ID를 부여한다. 프로젝트 시점·버전과 최종 이력서 작성 시점의 자료가 다른지 확인한다.
2. **주장별 검증:** 설계서의 검증 ID마다 근거·확인 절차·확인 결과·미해결 사항을 기록한다. 전체 프로젝트 성과와 본인 기여를 분리한다.
3. **필요한 재현만 수행:** 저장된 결과와 코드를 먼저 확인한다. 핵심 수치나 해석을 검증하는 데 필요한 소규모 재계산을 우선하고, 근거 없이 전체 재학습·새 프로젝트로 범위를 늘리지 않는다.
4. **개념 보충 조사:** 실제 사용 도구·버전을 먼저 파악한 뒤 공식 문서와 원자료를 찾는다. 최신 기본값을 과거 프로젝트의 설정으로 간주하지 않는다.
5. **자료집 작성:** 개념 → 실제 적용 → 판단 이유 → 검증 → 한계 → 질문 순으로 설명한다. 용어는 처음 등장할 때 한국어 뜻과 예시를 붙인다.
6. **면접 답변 제작:** 확인된 경험으로 30초 요약, 2분 설명, 꼬리질문 답변을 만든다. 미확인 수치는 빈칸이나 확인 필요로 남긴다.
7. **교차 점검:** 자료집·이력서·코드·결과표 사이에 역할, 날짜, 데이터 규모, 성과 표현이 일치하는지 확인한다.

각 자료집에는 `주장 ID / 주장 / 근거 ID / 검증 방법 / 확인 결과 / 상태 / 답변에 사용할 표현 / 남은 확인` 형식의 근거표를 둔다. 모든 근거가 확보되지 않아도 개념 설명과 확인된 부분은 작성할 수 있다. 미확인 부분을 임의로 메워 완료 처리하지 않는다.

## 5. 공통 편집 원칙

- 실무면접의 핵심인 데이터 추출·전처리·분석·기준 설계·검증·보고에 연결한다.
- 평가 우선순위는 **P0: 반드시 설명할 핵심 / P1: 중요한 꼬리질문 / P2: 시간 여유 시 심화**로 표시한다. 출제 확률로 표현하지 않는다.
- 모든 장은 `학습 목표 → 필요한 개념 → 나의 실제 적용 → 판단·검증 → 확인 문제`로 구성한다.
- 답변에는 실제 수행, 당시 생각, 현재의 개선안을 분리한다. 한계를 인정한 뒤 개선안을 말할 수 있게 구성한다.
- 확인 문제는 단순 암기보다 계산·표 해석·오류 찾기·판단 이유 설명 중심으로 만든다.
- 일반적인 SQL·통계 개념도 해당 경험의 실제 데이터·처리에 연결해 설명한다.
- 독립적인 기업 업무 케이스 자료집과 임원면접 종합 자료집은 이번 제작 범위에 포함하지 않는다.
- 외부에 보여줄 증거 화면은 연락처, 계정, API 키, 타인의 대화 등 면접 설명에 불필요한 정보를 제외한다.

## 6. 최종 자료집의 공통 구성

1. 경험 한눈에 보기: 목적·기간·역할·입력·처리·출력
2. 이력서 주장과 근거 지도
3. 실제 사용한 개념을 처음부터 설명하는 본문
4. 데이터·코드·판단 과정을 따라가는 예시
5. 검증 결과와 실패·예외 사례
6. 실무면접 예상 질문과 답변 근거
7. 30초·2분 설명 및 복습 문제
8. 미확인 사항·추가 학습·출처

분량을 먼저 고정하기보다 경험의 복잡도에 맞춘다. FinDone·공시·ETF는 방법과 검증을 자세히, HappyLLM은 데이터 구조·권한 검증·실제 기여를 중심으로 구성한다.
