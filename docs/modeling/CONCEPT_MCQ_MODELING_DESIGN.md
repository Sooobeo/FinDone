# FinDone 개념형 5지선다 모델링 기준

- 문서 버전: 3.1
- 기준일: 2026-08-13
- 구현 상태: v3.1 설계 확정, 타개념 Top-2 기준선·비율 실험과 540문항 preview 생성기 구현 완료. 공유 앵커·구별축·개념변형·역문항은 preview에서 자동 검사하고 예외만 별도 검수 큐로 출력한다. 사람 검수, Admin·문항은행·앱 반영은 미완료
- 적용 범위: 문항 유형, 참·거짓 설명 데이터, 개념 관계 그래프, 타개념 오답, 개념변형 오답, 랭커, 자동 검수, Admin, 앱용 SQLite

## 1. 설계 목표

FinDone의 개념형 문항은 용어를 문제로 제시하고 설명을 선지로 고르게 한다. 즉 문제 방향은 **용어 → 설명**이다. 문항은 두 능력을 함께 측정해야 한다.

1. 이름이나 일부 표현이 겹치는 다른 개념을 구분하는 능력
2. 해당 개념의 조건·대상·방향뿐 아니라 관련 개념과 맺는 짝·포함·적용·비교 관계를 정확히 이해하는 능력

따라서 오답을 모두 다른 개념의 설명으로 구성하지 않는다. 일반 문항에는 **타개념 혼동 오답**과 **해당 개념을 어긋나게 바꾼 개념변형 오답**을 같은 수로 넣는다.

다음 방향은 사용하지 않는다.

```text
문제: 설명 또는 수식
선지: 용어 5개
```

관계형 문항에서도 화면에 수식이나 변수식을 제시하지 않는다. 모든 관계는 **수식 없이 말로 풀어쓴 설명**으로 제시한다.

## 2. 최우선 문항 계약

### 2.1 올바른 설명을 고르는 일반 유형

`term_to_definition`, `term_to_intuition`, `term_to_verbal_relation`은 다음 구성을 고정한다.

```text
문제: 용어
선지: 같은 유형의 설명문 5개
채점상 정답: 해당 개념의 참인 설명 1개
오답 1~2: 일부 표현·구성요소·기능이 겹치는 다른 개념의 참인 설명 2개
오답 3~4: 해당 개념의 참인 설명을 그럴듯하게 어긋나게 바꾼 거짓 설명 2개
```

즉 일반 유형의 선지 구성은 `대상 개념 참 1 + 타개념 참 2 + 대상 개념 변형 거짓 2`다.

### 2.2 옳지 않은 설명을 고르는 역문항

새 유형 `term_to_incorrect_statement`를 추가한다.

```text
문제: 용어에 관한 설명 중 옳지 않은 것을 고르시오
내용상 참인 선지: 해당 개념의 검토된 설명 4개
내용상 거짓인 선지: 해당 개념의 참인 설명을 변형한 설명 1개
채점상 정답: 내용상 거짓인 개념변형 선지 1개
```

역문항에는 타개념 설명을 넣지 않는다. 다섯 선지가 모두 대상 개념을 설명하는 것처럼 보여야 하며, 조건·대상·방향 중 하나가 어긋난 선지를 찾아야 한다.

### 2.3 문장 진실성과 채점 정답의 분리

`옳지 않은 것` 유형에서는 “참인 문장”과 “선택해야 하는 정답”이 다르다. 따라서 `isCorrect` 하나로 두 의미를 표현하지 않는다.

| 문항 유형 | 문장 내용 | `statementTruth` | `isAnswer` |
|---|---|---|---|
| 일반 유형 | 대상 개념의 참인 설명 | `true` | `true` |
| 일반 유형 | 타개념의 참인 설명 | `true` | `false` |
| 일반 유형 | 대상 개념의 변형 거짓 설명 | `false` | `false` |
| 옳지 않은 것 | 대상 개념의 참인 설명 4개 | `true` | `false` |
| 옳지 않은 것 | 대상 개념의 변형 거짓 설명 1개 | `false` | `true` |

기존 `isCorrect`는 v3에서 폐기하고 `isAnswer`로 대체한다. Android의 채점 로직도 `statementTruth`가 아니라 `isAnswer`를 사용한다.

### 2.4 선지의 개념명 비노출 원칙

문제 본문에는 대상 용어를 표시하지만, 다섯 선지의 `text`에는 가능한 한 **개념 소스에 등록된 이름을 직접 쓰지 않는다**. 학습자가 이름의 반복이나 약어를 단서로 고르는 대신 설명의 의미를 판단하게 하기 위한 원칙이다.

- 대상 `targetElementId`의 제목·별칭·약어는 모든 선지에서 금지한다.
- 각 선지의 `sourceElementId` 제목·별칭·약어도 해당 선지에서 금지한다.
- 관계형의 `participantIds`가 가리키는 개념명도 기본적으로 숨기고 경제적 역할·기능·귀속 주체를 풀어 쓴다.
- 한글·영문·약어·띄어쓰기 제거형·대소문자 변형까지 같은 이름으로 정규화해 검사한다.
- 정확한 개념명과 ID는 내부 메타데이터, Admin 검수 화면, 정답 제출 후 해설에만 표시할 수 있다.

예를 들어 선지에는 `WACC로 할인한다` 대신 `부채 제공자와 주주가 요구하는 수익률을 조달 비중으로 합친 할인율로 현재가치화한다`고 쓴다. `FCFE는` 대신 `보통주주에게 귀속되는 현금흐름은`이라고 쓴다.

표준 고유명사를 빼면 문장의 의미가 달라지거나 모호해지는 경우에만 `nameExposureException`을 둘 수 있다. 예외에는 개념 ID, 노출 문자열, 대체 표현이 불가능한 이유, 사람 승인 상태를 저장한다. 대상 용어 또는 타개념 선지의 출처 개념명을 그대로 답처럼 노출하는 예외는 허용하지 않는다.

## 3. 문제 유형과 문항 수

각 요소마다 네 유형을 한 문항씩 생성한다.

| 유형 | 질문 | 선지 구성 | 요소당 문항 |
|---|---|---|---:|
| `term_to_definition` | 가장 정확한 정의 | 대상 참 1 + 타개념 참 2 + 대상 변형 거짓 2 | 1 |
| `term_to_intuition` | 가장 적절한 실무적 해석 | 대상 참 1 + 타개념 참 2 + 대상 변형 거짓 2 | 1 |
| `term_to_verbal_relation` | 수식 없이 설명한 핵심 관계 | 대상 참 1 + 타개념 참 2 + 대상 변형 거짓 2 | 1 |
| `term_to_incorrect_statement` | 옳지 않은 설명 | 대상 참 4 + 대상 변형 거짓 1 | 1 |

135개 요소 기준 총 문항 수는 `540개`다.

### 3.1 정의형

- 대상, 목적, 측정 범위, 경제적 실체를 묻는다.
- 타개념 오답도 정의형 사실만 사용한다.
- 개념변형 오답은 대상·범위·기준을 바꾸되 문법과 문체는 자연스러워야 한다.

### 3.2 직관형

- 실제 상황에서 어떻게 해석해야 하는지 묻는다.
- 타개념 오답은 비슷한 상황에서 쓰이지만 결론이나 관찰 대상이 다른 개념을 사용한다.
- 개념변형 오답은 원인과 결과, 현금과 회계 인식, 위험 부담 주체 등을 바꿀 수 있다.

### 3.3 관계형

- 관계형은 인과관계나 증가·감소 방향에 한정하지 않는다. 대상 개념이 유사하거나 관련 있는 개념과 어떤 역할로 연결되는지를 수식 없이 묻는다.
- 타개념 오답은 일부 참여 개념이나 경제적 대상이 겹치지만 다른 관계를 정확하게 설명해야 한다.
- 개념변형 오답은 검토된 관계에서 역할, 짝, 적용 대상, 포함 범위, 순서 중 하나만 바꾼다.
- 관계를 바꿀 때는 임의의 개념을 끼워 넣지 않고, 같은 관계군에서 역할상 혼동하기 쉬운 인접 개념을 사용한다.
- 등식, 부등식, LaTeX, 변수식, 계산식은 모든 선지에서 금지한다.

#### 3.3.1 관계 유형

| `relationType` | 확인하는 관계 | 예시 |
|---|---|---|
| `directional` | 조건이 변할 때 다른 대상이 같은 방향 또는 반대 방향으로 움직이는지 | 요구수익률과 현재가치 |
| `causal` | 한 사건이 다른 결과를 만드는지 | 외상대금 회수와 자산 구성 변화 |
| `application_pairing` | 측정치·할인율·가치 대상이 올바르게 짝지어지는지 | 기업 전체 현금흐름–가중평균자본비용–기업가치 |
| `composition_inclusion` | 어떤 항목이 구성에 포함되거나 제외되는지 | 영업자산 가치와 비영업자산 조정 |
| `bridge_conversion` | 한 가치·지표를 다른 가치·지표로 잇는 조정이 무엇인지 | 기업가치에서 지분가치로의 연결 |
| `sequence_timing` | 인식·평가·정산 과정의 순서와 기준 시점이 무엇인지 | 매출 인식과 현금 회수 |
| `comparison_boundary` | 비슷한 지표가 무엇을 공통으로 보고 어떤 범위에서 갈리는지 | 투하자본 수익성과 자기자본 수익성 |
| `equivalence_constraint` | 어떤 전제에서 두 표현이나 접근이 같은 경제적 결론에 이르는지 | 명목 기준 현금흐름과 명목 할인율의 일치 |
| `hierarchy_classification` | 상위·하위, 원천·측정치, 자산·청구권의 분류가 어떻게 연결되는지 | 영업자산과 기업 전체 가치 |

인과·방향형은 이 분류의 일부일 뿐 기본값이 아니다. 원천 자료가 여러 관계를 지원하면 `application_pairing`, `bridge_conversion`, `comparison_boundary`처럼 관련 개념의 역할을 구분하는 관계를 우선 후보에 포함한다.

#### 3.3.2 관련 개념 관계 변형

관계형 원자 사실은 문장만 저장하지 않고 참여 개념과 역할 연결을 함께 저장한다. 변형은 다음 원칙을 지킨다.

- 올바른 관계를 `참여 개념 + 역할 바인딩 + 관계 간선`으로 먼저 확정한다.
- 하나의 변형은 역할 바인딩 또는 관계 간선 하나만 바꾼다.
- 대체 개념은 같은 도메인이라는 이유만으로 고르지 않고, 동일 관계군에서 실제로 다른 역할을 맡는 인접 개념이어야 한다.
- 바꾼 뒤에도 다른 관행이나 특수 조건에서 참이 될 수 있으면 폐기한다.
- 한 문장에서 두 짝을 동시에 뒤바꿔 오류 지점을 찾기 어렵게 만드는 변형은 사용하지 않는다.

예를 들어 `FCFF·FCFE`에서는 현금흐름, 할인율, 가치 대상의 올바른 짝을 관계 사실로 둔다. `기업 전체에 귀속되는 현금흐름–가중평균자본비용–기업가치`에서 할인율 역할만 자기자본비용으로 바꾸는 것은 허용하지만, 세 역할을 모두 무작위로 바꾸는 것은 허용하지 않는다.

### 3.4 옳지 않은 것

- 문제 문구에 `옳지 않은 것`을 명확히 표시한다.
- 이중부정은 사용하지 않는다.
- 참인 네 선지는 서로 다른 원자 사실을 설명한다.
- 거짓인 한 선지는 하나의 핵심 주장만 변경한다.
- `항상`, `절대`, `전혀`처럼 정답을 쉽게 암시하는 표현은 원문 근거가 없으면 사용하지 않는다.

## 4. 선지 출처 유형

모든 선지는 다음 세 출처 유형 중 하나를 가진다.

### 4.1 `target_fact`

대상 개념의 검토된 참인 설명이다.

- `sourceElementId == targetElementId`
- `statementTruth == true`
- 검토 완료된 원자 사실과 출처가 있어야 한다.

### 4.2 `cross_concept_fact`

대상과 일부가 겹치지만 식별자가 다른 개념의 참인 설명이다.

- `sourceElementId != targetElementId`
- `statementTruth == true`
- 출처 개념에 대해서는 정확한 설명이어야 한다.
- 대상 개념과의 겹치는 지점과 다른 지점을 모두 기록해야 한다.

### 4.3 `target_mutation`

대상 개념의 참인 설명에서 하나의 핵심 주장을 바꾼 거짓 설명이다.

- `sourceElementId == targetElementId`
- `statementTruth == false`
- 원본 `baseFactId`, 변형 규칙, 변경된 주장, 거짓인 이유가 있어야 한다.
- 자유 창작한 문장은 사용할 수 없다.

## 5. 타개념 혼동 오답 규칙

타개념 오답은 단순히 같은 도메인에서 임의로 가져오지 않는다. 대상 개념과 **겹치는 앵커가 하나 이상 있으면서 개념 정체성은 다른 후보**만 허용한다.

### 5.1 허용하는 겹침 축

- **표면 용어 겹침**: `매출채권`과 `채권`처럼 핵심 단어 일부가 겹친다.
- **구성요소 겹침**: WACC와 자기자본비용처럼 같은 자본비용 체계의 일부를 공유한다.
- **측정대상 겹침**: ROIC와 ROE처럼 수익성을 측정하지만 투입자본의 범위가 다르다.
- **상황 겹침**: 재고자산과 매출채권처럼 운전자본 관리 상황을 공유하지만 경제적 대상이 다르다.
- **관계변수 겹침**: 현재가치와 채권 듀레이션처럼 금리와 가치가 함께 등장하지만 설명하는 관계가 다르다.
- **절차 겹침**: 기업가치 평가와 주주가치 평가처럼 같은 평가 과정에 속하지만 결과 범위가 다르다.

### 5.2 정의형의 출처 근거 기반 성격 호환

정의형 타개념 오답은 설명의 주제가 비슷하다는 이유만으로 선택하지 않는다. 대상이 자산·계정·청구권 같은 경제적 실체인데 후보가 비율·회전속도·성과지표처럼 측정 도구라면, 선지의 `지표다` 같은 표현만으로도 쉽게 제거할 수 있으므로 후보 단계에서 제외한다.

이 조건은 도메인이나 `mode`, 제목 키워드만 보고 임의의 `entityKind`를 부여하는 방식으로 구현하지 않는다. 대상과 후보 각각에 다음 출처 근거를 저장한다.

- `roleId`: 정의가 직접 선언하는 설명 역할
- `ruleId`: 명시적 정의 술어를 판독한 규칙 ID
- `sourceField`: 근거 필드. 현재 하드 필터는 검토된 `definition`만 사용
- `evidenceText`: `계정이다`, `금융상품이다`, `지표다`, `방법이다`처럼 실제로 일치한 구절
- `sourceLocator`: 해당 정의의 출처 위치
- `sourceSha256`: 판정에 사용한 정의문의 해시

하드 필터는 **대상과 후보 양쪽에 명시적인 출처 근거가 있을 때만** 작동한다. 두 역할이 호환되면 후보를 유지하고, `경제적 실체 ↔ 정량 측정치` 또는 `경제적 실체 ↔ 방법·절차`처럼 정의 질문에 답하는 성격이 다르면 `definition-role-mismatch`로 제외한다. 한쪽이라도 근거를 추출하지 못하면 임의로 추정하지 않고 후보를 유지하되 검수 자료에 `insufficient-source-evidence`로 남긴다.

따라서 `매출채권` 정의형에서 `채권`처럼 금융상품을 설명하는 후보는 경제적 실체라는 성격이 맞으므로 유지할 수 있다. 반면 `매출채권회전율`처럼 회수 속도를 나타내는 지표는 의미상 관련되어도 설명 성격이 다르므로 랭킹 전에 제외한다.

### 5.3 필수 구별 근거

각 타개념 후보에는 다음을 저장한다.

- `sharedAnchorIds`: 겹치는 용어·구성요소·상황 ID
- `overlapType`: 겹침 축
- `distinctAxis`: 대상과 출처 개념을 구분하는 핵심 차이
- `distinctnessRationale`: 왜 대상 개념의 정답이 될 수 없는지 설명
- `definitionRoleCompatibility`: 정의형에서 양쪽 출처 근거와 호환 판정

문자열 일부만 우연히 같고 의미상 겹침이 없는 후보는 제외한다. 반대로 의미상 거의 같은 별칭·상위하위 중복으로 두 선지가 동시에 맞을 수 있는 후보도 제외한다.

### 5.4 예시

```text
대상 용어: 매출채권

타개념 후보 1: 정부나 기업에 돈을 빌려주고 약정된 이자와 원금을 받는 금융상품이다.
- 출처 개념: 채권
- 겹침: 표면 용어 ‘채권’
- 차이: 영업상 외상매출에 대한 청구권과 자금조달 증권

타개념 후보 2: 판매를 위해 보유하거나 생산 과정에 있는 재화의 원가를 나타내는 영업자산이다.
- 출처 개념: 재고자산
- 겹침: 영업 과정에 묶이는 자산
- 차이: 고객에게 받을 금전 청구권과 판매를 위해 보유하는 재화

사전 제외 후보: 신용매출액이 평균 미수금 잔액에 비해 얼마나 빠르게 회수되는지 보여 주는 지표다.
- 출처 개념: 매출채권회전율
- 제외 사유: 대상은 자산·청구권이고 후보는 회수 효율 측정치이므로 `definition-role-mismatch`
```

## 6. 개념변형 오답 규칙

개념변형은 참인 원자 사실 하나에서 시작해 **최소한으로 바꾸되 확실히 거짓**이어야 한다.

### 6.1 허용하는 변형

- **방향 반전**: 커진다 ↔ 작아진다
- **원인·결과 교환**: 원인과 결과의 역할을 바꾼다.
- **대상 교환**: 기업 전체 ↔ 보통주주, 채권자 ↔ 주주 등 분석 대상을 바꾼다.
- **기준 교환**: 시장가치 ↔ 장부가, 세전 ↔ 세후, 명목 ↔ 실질, 총액 ↔ 순액
- **시점 교환**: 인식 시점, 회수 시점, 평가 기준 시점을 바꾼다.
- **조건 반전**: 성립 조건을 반대로 바꾸거나 필수 조건을 다른 조건으로 교체한다.
- **범위 변형**: 포함되는 항목과 제외되는 항목을 바꾼다.
- **분자·분모 의미 교환**: 수식을 쓰지 않고 “무엇을 무엇에 대비하는가”를 말로 뒤바꾼다.
- **현금·회계 인식 교환**: 현금 유입과 수익 인식, 비용 지급과 비용 인식을 혼동시킨다.
- **관계 역할 교환**: 같은 관계군의 참여 개념 중 할인율, 현금흐름, 측정대상 같은 역할 하나를 바꾼다.
- **적용 대상 교환**: 올바른 방법이나 지표를 기업 전체, 주주, 채권자 등 다른 대상에 연결한다.
- **짝 교환**: 서로 대응하는 측정치·기준·결과 중 한 짝만 관련 개념의 짝으로 교체한다.
- **포함 경계 교환**: 포함 항목과 제외 항목 또는 전체와 부분의 연결을 바꾼다.
- **브리지 조정 교환**: 한 가치에서 다른 가치로 넘어갈 때 더하거나 빼는 조정 항목 하나를 역할상 비슷한 항목으로 바꾼다.
- **순서 교환**: 관련 절차의 앞뒤 단계나 기준 시점 하나를 뒤바꾼다.
- **비교 축 교환**: 유사 지표의 공통 목적은 유지하면서 분모, 귀속 주체, 측정 범위 같은 구별 축 하나를 바꾼다.
- **계층 반전**: 상위·하위 또는 원천·결과의 연결 방향을 바꾼다.

### 6.2 금지하는 변형

- 원문 앞에 `아니다`만 붙이는 단순 부정
- 이중부정
- 철자 오류나 어색한 문법으로 정답을 암시하는 문장
- `항상`, `절대`만 추가해 쉽게 틀리게 만드는 문장
- 여러 주장을 동시에 바꿔 무엇이 틀렸는지 특정할 수 없는 문장
- 특수한 조건에서는 참이 될 수 있어 거짓이 확정되지 않는 문장
- 출처 근거 없이 새로운 수치·기간·임계값을 만드는 변형
- 관계형 문장에 수식이나 기호를 삽입하는 변형

### 6.3 변형 레코드의 필수 근거

모든 변형에는 다음이 있어야 한다.

- 참인 원본 문장
- 바뀐 구절
- 변형 규칙 ID
- 거짓인 이유
- 반례 또는 원본 출처의 지지 문장
- 독립 검수 상태

자동 생성기는 변형 후보를 만들 수 있지만, 거짓임을 증명하지 못한 후보를 문항에 넣을 수 없다.

## 7. 문항 예시

### 7.1 일반 정의형

```text
다음 중 ‘매출채권’을 가장 정확하게 설명한 것은?

A. 상품이나 서비스를 외상으로 판매해 아직 받지 못한 고객 대금을 나타내는 자산이다. [채점상 정답·참]
B. 정부나 기업에 돈을 빌려주고 약정된 이자와 원금을 받는 금융상품이다. [타개념·참]
C. 판매를 위해 보유하거나 생산 과정에 있는 재화의 원가를 나타내는 영업자산이다. [타개념·참]
D. 고객에게 상품을 인도하기 전에 미리 받은 대금을 나타내는 자산이다. [대상 변형·거짓]
E. 고객이 외상대금을 현금으로 지급하면 이 잔액이 증가한다. [대상 변형·거짓]
```

B는 `채권`, C는 `재고자산`을 정확히 설명한다. 둘 다 매출채권과 같은 경제적 실체를 정의하면서 각각 자금조달 증권과 판매용 재화라는 구별 축이 있다. 회수 효율을 설명하는 `매출채권회전율`은 지표라는 성격만으로 제거할 수 있으므로 정의형 후보에서 제외한다. D와 E는 매출채권의 대상과 방향을 각각 바꾼 변형이다.

### 7.2 옳지 않은 것

```text
다음 중 ‘매출채권’에 관한 설명으로 옳지 않은 것은?

A. 외상매출이 발생하고 현금을 아직 받지 못하면 잔액이 생길 수 있다. [참]
B. 일반적으로 영업 과정에서 발생하는 유동자산으로 분류될 수 있다. [참]
C. 고객에게서 외상대금을 회수하면 매출채권은 줄고 현금은 늘어난다. [참]
D. 회수 가능성이 낮아지면 손실 가능성과 대손 평가를 함께 살펴야 한다. [참]
E. 고객에게서 외상대금을 회수하면 매출채권과 현금이 함께 증가한다. [채점상 정답·거짓]
```

역문항에서 A~D는 내용상 옳지만 채점상 답은 아니다. E만 내용상 거짓이며 사용자가 선택해야 하는 답이다.

### 7.3 관련 개념 관계형

```text
다음 중 ‘FCFF·FCFE’의 핵심 관계를 가장 정확하게 설명한 것은?

A. 채권자와 주주에게 함께 귀속되는 현금흐름은 두 자금 제공자의 요구수익률을 조달 비중으로 합친 할인율로 현재가치화해 기업 전체의 몫과 연결하고, 보통주주에게만 귀속되는 현금흐름은 그 주주가 요구하는 수익률로 현재가치화해 보통주 몫과 연결한다. [채점상 정답·참]
B. 부채 제공자와 주주가 각각 요구하는 수익률을 조달 비중에 따라 합쳐 기업 전체 투자자가 요구하는 수익률을 정한다. [타개념·참]
C. 영업자산 전체가 만들어내는 가치에서 이자부 부채를 빼고 여유 현금을 더해 보통주주 몫을 구한다. [타개념·참]
D. 채권자와 주주에게 함께 귀속되는 현금흐름은 보통주주만의 요구수익률로 현재가치화해 기업 전체의 몫과 연결한다. [대상 관계 변형·거짓]
E. 보통주주에게만 귀속되는 현금흐름은 그 주주가 요구하는 수익률로 현재가치화해 채권자와 주주 전체의 몫과 연결한다. [대상 관계 변형·거짓]
```

B와 C는 각각 `WACC`, `기업가치–지분가치 브리지`에 대한 참인 관계다. D는 할인율 역할을, E는 가치 대상 역할을 같은 평가 관계군의 인접 개념으로 바꾼 선지다. 두 변형 모두 인과 방향을 뒤집은 것이 아니라 **관련 개념의 올바른 짝을 하나씩 바꾼 것**이다.

## 8. 원자 사실 데이터 계약

역문항의 참인 선지 네 개를 만들려면 요소마다 최소 네 개의 독립적인 원자 사실이 필요하다. 긴 정의나 직관 문장을 그대로 네 번 재사용하지 않고, 검토된 콘텐츠를 단일 주장 단위로 분해한다.

```json
{
  "factId": "CF-10:discounting_pair:01",
  "elementId": "CF-10",
  "factType": "verbal_relation",
  "claimType": "relation_mapping",
  "relationType": "application_pairing",
  "participantIds": [
    "CF-10:fcff",
    "CF-07:wacc",
    "CF-12:enterprise_value"
  ],
  "roleBindings": {
    "cashFlow": "CF-10:fcff",
    "discountRate": "CF-07:wacc",
    "valueTarget": "CF-12:enterprise_value"
  },
  "relationEdges": [
    {
      "from": "CF-10:fcff",
      "predicate": "discounted_with",
      "to": "CF-07:wacc"
    },
    {
      "from": "CF-10:fcff",
      "predicate": "connects_to",
      "to": "CF-12:enterprise_value"
    }
  ],
  "text": "채권자와 주주에게 함께 귀속되는 현금흐름은 두 자금 제공자의 요구수익률을 조달 비중으로 합친 할인율로 현재가치화해 기업 전체의 몫과 연결한다.",
  "sourceIds": ["..."],
  "sourceLocator": "...",
  "reviewStatus": "reviewed",
  "contentSha256": "..."
}
```

`participantIds`는 검토된 요소 ID 또는 요소 내부의 승인된 하위 개념 ID만 참조한다. 관계형이 아닌 원자 사실은 `relationType`, `participantIds`, `roleBindings`, `relationEdges`를 생략할 수 있다. 관계형은 네 필드를 모두 가져야 하며 문장과 구조화된 관계가 같은 내용을 뜻해야 한다.

릴리스 가능한 원자 사실은 다음을 충족해야 한다.

- 한 문장에 핵심 주장 하나
- 독립적인 출처 추적 가능
- 대상·출처·관계 참여 개념의 이름과 별칭을 선지에 직접 노출하지 않음
- 불가피한 표준 고유명사 노출은 승인된 `nameExposureException`으로 추적
- 수식 없이 이해 가능
- 다른 원자 사실과 의미가 중복되지 않음

## 9. 개념변형 데이터 계약

```json
{
  "mutationId": "ACC-08:collection_effect:direction_reverse:01",
  "targetElementId": "ACC-08",
  "baseFactId": "ACC-08:collection_effect:01",
  "mutationRuleId": "direction_reverse",
  "text": "고객에게서 외상대금을 회수하면 매출채권과 현금이 함께 증가한다.",
  "changedClaim": "매출채권은 줄고 → 매출채권도 늘고",
  "falsityRationale": "현금 회수는 자산의 구성을 매출채권에서 현금으로 바꾸므로 매출채권 잔액은 감소한다.",
  "statementTruth": false,
  "reviewStatus": "reviewed",
  "contentSha256": "..."
}
```

변형은 원본 사실의 출처를 상속하지만, `reviewStatus`는 별도로 관리한다. 원본이 검토됐다고 변형까지 자동으로 검토 완료로 간주하지 않는다.

관계 변형은 일반 변형 필드에 변경 전후 관계를 추가한다.

```json
{
  "mutationId": "CF-10:discounting_pair:role_binding_swap:01",
  "targetElementId": "CF-10",
  "baseFactId": "CF-10:discounting_pair:01",
  "mutationRuleId": "role_binding_swap",
  "relationType": "application_pairing",
  "changedRelation": {
    "operation": "replace_role_binding",
    "role": "discountRate",
    "beforeParticipantId": "CF-07:wacc",
    "afterParticipantId": "CF-10:cost_of_equity"
  },
  "text": "채권자와 주주에게 함께 귀속되는 현금흐름은 보통주주만의 요구수익률로 현재가치화해 기업 전체의 몫과 연결한다.",
  "falsityRationale": "기업 전체의 채권자와 주주에게 귀속되는 현금흐름에는 두 자금 제공자의 요구수익률을 반영한 가중평균자본비용을 대응시켜야 한다.",

  "contentSha256": "..."

```

`beforeParticipantId`와 `afterParticipantId`는 같은 관계군에서 역할상 비교 가능한 개념이어야 한다. 변경 전후 값과 거짓 근거가 일치하지 않거나 두 개 이상의 역할이 바뀐 레코드는 릴리스할 수 없다.

## 11. 후보 생성 파이프라인

### 11.1 공통 전처리

1. 대상 요소의 검토된 콘텐츠를 원자 사실로 분해한다.
2. 수식이 있는 관계를 검토된 자연어 관계로 변환한다.
3. 용어명·별칭·요소 코드가 화면 문장에 노출된 사실을 제외한다.
4. 대상·출처·관계 참여 개념명을 역할·기능 중심의 화면 문장으로 바꾼다.
5. 이름 정규화 사전으로 화면 문장을 다시 검사하고 승인되지 않은 노출을 제외한다.
6. 중복·유사 사실을 묶고 독립 주장을 남긴다.
7. 사실과 변형을 동일한 seed에서 결정론적으로 생성한다.

### 11.2 타개념 후보

1. 대상과 다른 `elementId`만 후보로 둔다.
2. 같은 사실 유형만 사용한다.
3. 공유 앵커가 없는 후보를 하드 필터로 제외한다.
4. 개념 정체성이 사실상 같은 별칭·중복 요소를 제외한다.
5. 정의형이면 대상과 후보의 출처 정의에서 명시적 설명 역할과 근거 구절을 추출한다.
6. 양쪽 근거가 모두 있으면서 설명 역할이 호환되지 않는 후보를 `definition-role-mismatch`로 제외한다.
7. 근거가 부족한 후보는 추정으로 제외하지 않고 `insufficient-source-evidence`로 기록한다.
8. 겹침 강도와 구별 가능성을 함께 랭킹한다.
9. 출처 개념에 대해 참인지 검증한다.
10. 일반 유형 한 문항당 두 개를 선택한다.

### 11.3 개념변형 후보

1. 대상 개념의 참인 원자 사실에서 시작한다.
2. 허용된 변형 규칙 하나만 적용한다.
3. 바뀐 구절과 거짓인 이유를 기록한다.
4. 문법·길이·문체를 원본과 맞춘다.
5. 원본과 너무 비슷해 차이를 찾을 수 없거나 너무 노골적인 변형을 제외한다.
6. 일반 유형에는 같은 사실 유형의 변형 두 개를 선택한다.
7. 역문항에는 네 참인 사실 중 하나에서 파생된 변형 한 개를 선택한다.

### 11.4 관계형 후보

1. 출처가 지지하는 관계를 3.3.1의 `relationType`으로 분류한다.
2. 문장에 등장하는 관련 개념을 승인된 참여 ID와 역할 바인딩으로 연결한다.
3. 관계 그래프에서 동일 관계군의 인접 개념과 역할 호환 후보를 검색한다.
4. 타개념 후보는 참여 개념이 일부 겹치되 대상과 다른 참인 관계를 선택한다.
5. 대상 변형 후보는 역할 바인딩 또는 관계 간선 하나만 교체한다.
6. 바뀐 관계가 일반적 전제와 허용된 대안 관행에서도 거짓인지 검증한다.
7. 인과·방향형으로만 후보가 몰리지 않도록 관계 유형별 후보 수와 채택 수를 기록한다.

## 12. 모델링 구조

v3는 하나의 랭커가 모든 오답을 고르는 구조를 사용하지 않는다.

```text
검토된 원자 사실·관계 그래프
  ├─ 타개념 후보 검색 → overlap/distinctness 하드 필터 → cross-concept ranker → 2개
  ├─ 대상 사실 변형 → falsity verifier → mutation ranker → 2개 또는 1개
  └─ 문항 조합기 → 선지 균형·복수정답·누출 검사 → 문항은행
```

### 12.1 타개념 랭커

기존 word/char TF-IDF, 임베딩, 동일 도메인, 문체·길이 feature를 재사용할 수 있다. 다음 feature를 추가한다.

- 공유 앵커 수와 유형
- 공유 앵커가 문장 핵심부에 있는지 여부
- 대상과 출처 개념의 구별 축
- 상위·하위·별칭 중복 위험
- 대상 설명에도 맞을 가능성

임베딩 유사도만 높고 명시적인 겹침 근거가 없는 후보는 선택하지 않는다.

#### 12.1.1 코퍼스 기반 예외 감사 기준

공유 앵커의 구체성은 고정된 임의 개수나 목표 검수율로 정하지 않는다. 실행 시점의 검토 대상 코퍼스에서 각 명시 앵커가 출현한 요소 수(`documentFrequency`)를 계산하고, **nearest-rank 75백분위**를 흔한 앵커 감사 기준으로 사용한다.

- 앵커 빈도 표본 수를 `N`이라 할 때 순위는 `ceil(0.75 × N)`이다.
- 선택된 타개념 선지의 모든 공유 앵커가 이 p75보다 흔하면 `common-anchor-only` 소프트 예외다.
- 요소 전체 출처에는 공유 앵커가 있지만 대상 정답문과 실제 타개념 선지문 사이에 명시 앵커 교집합이 0개면 `no-displayed-fact-anchor-overlap` 소프트 예외다.
- 정의형의 대상 또는 후보에서 검토된 정의 종결 술어를 추출하지 못하면 `definition-insufficient-source-evidence` 소프트 예외다.
- 위 세 기준은 검수 우선순위를 정하는 소프트 기준이다. 5장의 공유 앵커 1개 이상과 양쪽 구별축 1개 이상 하드 게이트를 완화하거나 대체하지 않는다.
- 실행 기록에는 `N`, nearest-rank 순위, 산출 p75, 앵커별 문서빈도, 판정식, 사유별 문항 수를 모두 남긴다.
- 예외 수는 모델 점수, 목표 검수율, 원하는 절대 문항 수에 맞추지 않는다.

### 12.2 변형 검증기와 랭커

변형 후보는 유사도보다 다음을 우선한다.

- 원본 사실과 정확히 한 핵심 주장만 다른가
- 변형 후 거짓임을 출처로 설명할 수 있는가
- 관계형이면 정확히 하나의 역할 바인딩 또는 간선만 달라졌는가
- 대체 참여 개념이 같은 관계군의 실제 인접 개념인가
- 특수한 조건에서 참이 될 여지가 없는가
- 문법과 문체가 자연스러운가
- 너무 쉬운 부정 단서가 없는가
- 다른 네 선지와 길이·구체성이 비슷한가

자유 생성 모델의 점수만으로 변형을 릴리스하지 않는다. 규칙 기반 변형과 사람 검토된 변형 은행을 baseline으로 삼는다.

### 12.3 기준선과 최적화

- 타개념 랭커는 동일 가중 RRF 기준선에서 다시 시작한다.
- 변형 랭커는 허용 규칙 동일 가중 기준선에서 시작한다.
- 일반 유형의 `타개념 2 + 변형 2` 비율은 탐색 대상이 아니라 고정 계약이다.
- 역문항의 `참 4 + 변형 거짓 1` 비율도 고정 계약이다.
- validation으로 랭커와 가중치를 선택하고 test는 최종 구성에 한 번만 사용한다.
- v2 지표와 직접 비교하지 않고 v3 신규 기준선을 만든다.

## 13. 데이터 분할과 누출 방지

- 분할 단위는 `targetElementId`다.
- 한 요소의 원자 사실, 변형, 네 유형 문항은 모두 같은 split에 둔다.
- 같은 `baseFactId`에서 나온 변형이 여러 split에 걸치면 안 된다.
- test 요소에서 파생한 변형의 사람 검수 결과를 랭커 선택에 사용하지 않는다.
- 타개념 후보 사실은 검색 코퍼스에 존재할 수 있지만, test 문항의 적합도 라벨은 train·validation 학습에 사용하지 않는다.
- 같은 문장이나 의미상 같은 변형이 train과 test에 중복되지 않는지 fingerprint로 검사한다.

## 14. 평가 지표

전체 점수 하나로 두 오답 체계를 합치지 않고 유형별로 나눠 기록한다.

### 14.1 일반 랭킹 지표

- Recall@K
- NDCG@4
- Precision@4
- MRR

### 14.2 타개념 오답 지표

- 공유 앵커 충족률
- 다른 `elementId` 충족률
- 출처 개념 사실 정확도
- 대상 개념 비정답률
- 두 타개념 오답의 중복률
- 정의형 출처 역할 근거 보유율
- 정의형 역할 호환률과 `definition-role-mismatch` 사전 제외 수
- `insufficient-source-evidence` 후보의 사람 검수 결과
- 사람 검토 혼동 적합도

### 14.3 개념변형 지표

- 거짓 확정률
- 단일 주장 변형률
- 변형 규칙 추적률
- 문법·문체 통과율
- 모호하거나 조건부 참인 변형 수
- 사람 검토 난이도·그럴듯함 점수

### 14.4 관계형 지표

- 관계 유형별 원천 사실 수·후보 수·최종 채택 수
- 비인과 관계형 후보 보유 요소 커버리지
- `participantIds`, `roleBindings`, `relationEdges` 완전성
- 문장과 구조화 관계의 의미 일치율
- 관련 개념 대체율
- 단일 역할 또는 단일 간선 변형률
- 잘못된 짝의 거짓 확정률
- 대안 관행에서 참이 되는 관계 변형 수

### 14.5 역문항 지표

- 참인 선지 정확히 4개
- 거짓인 선지 정확히 1개
- `isAnswer`와 `statementTruth` 역관계 일치
- 이중부정 0건
- 정답만 길이·단정어·문체가 튀는 단서 0건

사람 라벨이 없는 약지도 점수는 엔지니어링 진단값이며 실제 교육 정확도로 표현하지 않는다.

## 15. 자동 품질 검사

모든 문항에 다음 하드 게이트를 적용한다.

- 지원되는 네 `questionType` 중 하나인지 확인
- 선지가 정확히 다섯 개인지 확인
- `isAnswer == true`가 정확히 하나인지 확인
- `answerChoiceKey`가 실제 답과 일치하는지 확인
- 각 선지의 `statementTruth`가 명시됐는지 확인
- 일반 유형의 출처 구성이 `target_fact 1 + cross_concept_fact 2 + target_mutation 2`인지 확인
- 역문항의 출처 구성이 `target_fact 4 + target_mutation 1`인지 확인
- 역문항의 답만 `statementTruth == false`인지 확인
- 타개념 선지의 출처 요소가 대상과 다른지 확인
- 타개념 선지에 공유 앵커와 구별 근거가 있는지 확인
- 정의형 타개념 선지가 출처 근거상 대상과 호환되는 설명 역할인지 확인
- 정의 역할 판정마다 근거 구절·출처 locator·입력 해시가 있는지 확인
- 근거가 없는 개념을 임의 분류해 하드 필터하지 않았는지 확인
- 변형 선지의 출처 요소가 대상과 같은지 확인
- 변형 선지에 원본 사실·규칙·거짓 근거가 있는지 확인
- 관계형 사실에 관계 유형·참여 개념·역할 바인딩·관계 간선이 모두 있는지 확인
- 관계형 문장과 구조화된 관계가 같은 의미인지 확인
- 관계 변형이 역할 바인딩 또는 간선 하나만 바꾸는지 확인
- 관계 변형의 대체 개념이 같은 관계군의 인접 개념인지 확인
- 대상·출처·관계 참여 개념의 제목·별칭·약어·요소 코드가 선지에 노출되지 않았는지 확인
- 개념명 노출 예외가 있다면 사유와 사람 승인이 모두 있는지 확인
- 관계형 선지에 수식·LaTeX가 없는지 확인
- 중복 선지와 복수 정답 가능성이 없는지 확인
- 같은 seed에서 문항은행 SHA-256이 재현되는지 확인

하드 게이트 위반은 Owner가 승인으로 덮을 수 없다. 원자 사실이나 변형을 수정하고 문항을 다시 생성해야 한다.

## 16. 사람 검수와 릴리스 게이트

v3 문항은 새 fingerprint와 `reviewInputSha256`을 사용한다. v2의 문항 승인·반려·수정·배치 승인은 v3에 승계하지 않는다.

특히 처음 도입하는 개념변형은 거짓 여부와 모호성을 사람이 확인해야 한다. 자동 검수는 명백한 오류를 줄이지만 거짓임을 완전히 대신 증명하지 않는다.

| 게이트 | 기준 |
|---|---:|
| 요소별 문항 수 | 4개 |
| 전체 문항 수 | 540개 |
| 문제 방향 위반 | 0건 |
| 선지 5개·답 1개 위반 | 0건 |
| 일반 유형의 1+2+2 구성 위반 | 0건 |
| 역문항의 참 4+거짓 1 구성 위반 | 0건 |
| 타개념 공유 앵커·구별 근거 누락 | 0건 |
| 정의형 출처 역할 불일치 선지 | 0건 |
| 근거 없는 정의 역할 하드 필터 | 0건 |
| 변형 원본·규칙·거짓 근거 누락 | 0건 |
| 관계 구조 필드 또는 변경 전후 관계 누락 | 0건 |
| 관계 변형의 다중 역할·간선 변경 | 0건 |

| 승인되지 않은 개념명·별칭·약어·코드 누출 | 0건 |

모든 조건을 충족하기 전에는 문항은행을 `release_ready`로 바꾸거나 APK를 게시할 수 없다.

## 17. Admin 요구사항

Admin 문항 검수 화면은 다음을 구분해 보여 준다.

- 문항 유형과 긍정·역문항 여부
- `statementTruth`와 `isAnswer`
- `target_fact`, `cross_concept_fact`, `target_mutation` 출처 유형
- 타개념 선지의 출처 개념, 공유 앵커, 구별 근거
- 정의형 대상·후보의 역할 판정, 실제 근거 구절, 출처, 호환·제외 사유
- 변형 선지의 원본 문장, 변경 구절, 변형 규칙, 거짓인 이유
- 관계형 사실의 관계 유형, 참여 개념, 역할 바인딩, 관계 간선
- 관계 변형의 변경 역할과 변경 전·후 개념
- 화면 선지에서 숨긴 개념명 목록과 `nameExposureException`
- 자동 검수 사유와 사람 승인·반려 상태

Excel export에도 같은 필드를 포함한다. 검수자는 화면에서 선지를 수정할 때 출처 사실과 변형 근거를 잃지 않아야 한다.

## 18. 앱용 SQLite와 Android

SQLite의 선지 스키마는 최소한 다음 필드를 저장한다.

- `source_kind`
- `source_element_id`
- `source_fact_id`
- `mutation_id`
- `statement_truth`
- `is_answer`
- `text`
- `explanation`

Android는 `is_answer`로 채점한다. `옳지 않은 것` 유형에서 참인 네 선지를 정답으로 처리하면 안 된다.

앱 화면은 다음을 지킨다.

- `옳지 않은 것` 문구를 명확하게 강조한다.
- 선택 전에는 참·거짓, 출처 개념, 변형 규칙을 숨긴다.
- 선택 전 선지에는 대상·출처·관계 참여 개념의 이름을 직접 노출하지 않는다.
- 선택 후에는 각 선지가 왜 참인지 또는 어떤 주장이 바뀌어 거짓인지 설명한다.
- 긴 설명형 선지는 잘리지 않고 여러 줄로 표시한다.
- 문항은행이 `release_ready`가 아니면 release APK 생성과 게시를 차단한다.

## 19. 버전 전환 범위

v3는 v2 문항은행 위에 선지만 일부 추가하는 패치가 아니다. 후보 단위와 채점 의미가 바뀌므로 새 계약으로 재생성한다.

재사용할 수 있는 항목:

- 검토된 135개 금융 요소와 출처
- 기존 정의·직관·자연어 관계 사실
- TF-IDF·임베딩 인코더 후보와 실험 인프라
- 타개념 후보 랭커의 feature 일부
- Admin 검수·수정·Excel export 인프라

새로 만들어야 하는 항목:

- 원자 사실 분해 데이터
- 공유 앵커와 구별 축 데이터
- 관련 개념 관계 그래프와 승인된 역할 바인딩
- 개념변형 규칙과 변형 후보 은행
- `statementTruth`와 `isAnswer`를 분리한 스키마
- 역문항 생성기와 검증기
- 타개념·변형 분리 랭커 및 평가
- v3 문항 fingerprint, 실험 보고서, Owner 검수

v2 임베딩 모델 파일을 후보로 재사용할 수는 있지만, v2의 최적점·지표·Owner 결정은 v3 결과로 간주하지 않는다.

## 20. 구현 순서

1. 이 문서를 v3 단일 기준으로 확정한다.
2. 기존 사실을 원자 주장 단위로 분해하고 요소별 최소 네 개를 확보한다.
3. 개념 간 공유 앵커·구별 축을 생성하고 검수한다.
4. 정의형의 출처 근거 기반 설명 역할과 호환 필터를 구현한다.
5. 관련 개념 관계 그래프와 관계 유형·역할 바인딩을 생성하고 검수한다.
6. 허용된 개념변형 규칙과 거짓 근거 스키마를 구현한다.
7. `statementTruth`, `isAnswer`, `sourceKind` 중심으로 문항·SQLite 계약을 변경한다.
8. 타개념 overlap 필터와 랭커를 구현한다.
9. 개념변형 생성기, 거짓 검증기, 변형 랭커를 구현한다.
10. 관계형의 인접 개념 검색, 역할 교환, 단일 간선 검증을 구현한다.
11. 세 일반 유형을 `1+2+2` 구성으로 재생성한다.
12. `term_to_incorrect_statement`을 `참 4+거짓 1` 구성으로 생성한다.
13. Admin에서 출처·겹침·관계·변형 근거를 수정·검수할 수 있게 한다.
14. Android 채점과 해설을 새 필드에 맞춘다.
15. 동일 가중 baseline부터 validation 탐색과 고정 test를 다시 수행한다.
16. Owner 검수와 현재 배치 승인이 끝난 뒤에만 APK를 릴리스한다.

## 21. 완료 정의

다음 조건을 모두 만족해야 v3 모델링이 완료된 것으로 본다.

- 135개 요소마다 네 유형, 총 540개 문항이 있다.
- 일반 유형이 대상 참 1, 겹치는 타개념 참 2, 대상 변형 거짓 2로 구성된다.
- 역문항이 대상 참 4, 대상 변형 거짓 1로 구성된다.
- 타개념 오답마다 실제 겹침 근거와 명확한 구별 축이 있다.
- 정의형 타개념 오답은 출처 정의에 근거해 설명 역할이 호환되며 근거 없는 임의 분류가 없다.
- 개념변형 오답마다 원본 사실, 변경 규칙, 거짓 근거가 있다.
- 문장 진실성과 채점 답이 데이터에서 분리된다.
- 관계형 선지는 수식 없이 방향·인과·짝·포함·브리지·순서·비교 관계를 자연어로 설명한다.
- 관계형 원자 사실은 관련 개념과 역할 연결이 구조화되어 있고, 관계 변형은 그중 하나만 바꾼다.
- 원천이 지원하는 요소에는 인과·방향형 외의 관련 개념 관계 후보가 포함된다.
- 선지는 대상·출처·관계 참여 개념명을 역할 설명으로 바꾸며, 승인되지 않은 이름 노출이 없다.
- 독립 test와 자동 품질 검사를 통과한다.
- Owner 예외 검수와 배치 승인이 끝난다.
- 동일 입력에서 문항은행과 SQLite 해시가 재현된다.
- Admin과 Android가 동일한 v3 계약을 표시한다.
- 릴리스 manifest가 `release_ready`다.
