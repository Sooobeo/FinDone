# FinDone 개념형 5지선다 모델링 기준

- 문서 버전: 2.0
- 기준일: 2026-08-12
- 구현 상태: 재설계 기준 확정, 새 모델 구현 전
- 적용 범위: 문제 유형, 설명 선지 데이터, 오답 랭커, 자동 검수, Admin 실험 이력, 앱용 SQLite

## 1. 최우선 문항 계약

FinDone의 모든 개념형 문항은 **용어를 문제로 제시하고 설명을 선지로 고르는 방식**으로 만든다.

```text
문제: 용어
선지: 해당 용어를 설명하는 문장 5개
정답: 제시된 용어를 정확히 설명하는 문장 1개
오답: 다른 개념을 정확히 설명하지만 제시된 용어에는 맞지 않는 문장 4개
```

예시는 다음과 같다.

```text
다음 중 ‘WACC’를 가장 정확하게 설명한 것은?

A. 영업활동과 재투자 뒤에 주주에게 남는 현금을 나타낸다.
B. 채권자와 주주가 요구하는 수익률을 각 조달원의 시장가치 비중에 따라 합친 자본비용이다. [정답]
C. 명시적 예측기간 이후의 모든 현금흐름을 한 시점의 가치로 요약한다.
D. 회계이익이 실제 영업현금으로 전환되는 정도를 나타낸다.
E. 비교기업의 시장 배수를 목표기업 지표에 적용해 가치를 추정한다.
```

다음 방향은 사용하지 않는다.

```text
문제: 설명 또는 수식
선지: 용어 5개
```

기존 `definition_to_term`, `intuition_to_term`, `core_relation_to_term` 문항과 그 실험·검수 결과는 v2에 승계하지 않는다.

## 2. 화면에 보이는 정보와 내부 정보

### 사용자에게 보이는 정보

- 문제에는 대상 용어와 공통 질문 문구만 표시한다.
- 선지에는 설명문만 표시한다.
- A~E 다섯 선지는 같은 설명 유형과 비슷한 문체로 맞춘다.
- 채점 전에는 선지의 출처 개념명, 요소 코드, 정답 여부를 표시하지 않는다.

### 내부에서만 사용하는 정보

- 대상 `elementId`
- 각 선지의 출처 `elementId`와 `factId`
- 정답 여부
- 출처 locator와 콘텐츠 해시
- 문항 fingerprint와 검수 입력 해시

내부 ID는 정답 추적과 출처 검증에 사용하되 앱의 문제 화면에는 노출하지 않는다.

## 3. 문제 유형

초기 v2 문항 유형은 다음 세 가지다. 세 유형 모두 문제 방향은 `용어 → 설명`으로 동일하다.

### 3.1 `term_to_definition`

용어의 정체, 목적, 적용 범위를 고르는 유형이다.

- 문제 예시: `다음 중 ‘현금전환주기’를 가장 정확하게 정의한 것은?`
- 정답 선지: 개념이 무엇을 측정하거나 설명하는지 한두 문장으로 기술한다.
- 오답 선지: 같은 금융 분야의 다른 개념 정의를 사용한다.
- 금지: 용어명 반복, 사전식 순환 정의, 수식, 정답만 유난히 긴 문장

### 3.2 `term_to_intuition`

용어를 실제 상황에서 어떻게 이해해야 하는지 고르는 유형이다.

- 문제 예시: `다음 중 ‘발생주의’를 가장 적절하게 해석한 것은?`
- 정답 선지: 실무적 의미, 경제적 직관, 흔한 해석상 주의를 설명한다.
- 오답 선지: 비슷한 상황에서 혼동하기 쉬운 다른 개념의 직관을 사용한다.
- 금지: 용어명을 그대로 되풀이하는 문장, 정의 선지와 사실상 같은 문장, 정답을 암시하는 코드나 약어

### 3.3 `term_to_verbal_relation`

용어의 핵심 수식이나 변수 관계를 **수식 없이 말로 풀어쓴 설명** 중에서 고르는 유형이다.

- 문제 예시: `다음 중 ‘현재가치’의 핵심 관계를 올바르게 설명한 것은?`
- 정답 선지 예시: `미래에 받을 금액이 클수록 현재가치는 커지고, 기다리는 기간이나 요구수익률이 높아질수록 현재가치는 작아진다.`
- 오답 선지: 다른 개념의 방향 관계 또는 핵심 조건을 말로 설명한다.
- 금지: 등식, 부등식, LaTeX, 변수식, 계산식, 수식 일부를 문장에 끼워 넣는 표현

`core_relation` 원문에 수식이 있더라도 화면용 선지에는 그대로 복사하지 않는다. 먼저 검토된 `verbal_relation` 사실로 변환한 뒤 사용한다.

## 4. 관계 설명 작성 규칙

관계형 선지는 숫자를 계산하게 하는 문항이 아니라 변수 사이의 방향과 조건을 이해했는지 확인한다.

### 허용하는 표현

- `A가 커질수록 B도 커진다.`
- `A가 커질수록 B는 작아진다.`
- `A의 비중이 클수록 전체 결과에 미치는 영향도 커진다.`
- `다른 조건이 같다면 기간이 길어질수록 효과가 누적된다.`
- `기준값이 결과값보다 커야 이 관계가 성립한다.`
- `두 값이 같은 방향으로 움직인다.`
- `한 값이 늘면 다른 값은 반대 방향으로 움직인다.`

### 금지하는 표현

- `A = B + C`, `P = C / r`, `r > g` 같은 식
- `$...$`, `$$...$$`, `\(...\)`, `\[...\]` 같은 LaTeX 구분자
- `=`, `<`, `>`, `≤`, `≥`, `∑`, `√`를 이용한 관계 표기
- 기호만 풀어 쓰고 사실상 계산식을 유지한 문장
- 계산에 필요한 숫자와 변수를 나열하는 문장

### 변환 원칙

1. 수식에서 결과 변수와 원인 변수를 구분한다.
2. 각 원인 변수가 증가할 때 결과가 어느 방향으로 움직이는지 적는다.
3. 관계가 성립하는 전제조건을 자연어로 함께 적는다.
4. 기호 대신 금융 용어의 전체 이름을 사용한다.
5. 계산 절차가 아니라 경제적 의미가 드러나는 한두 문장으로 마무리한다.
6. 변환 결과는 원문과 별도의 검토 대상 사실로 저장한다.

## 5. 선지 작성 규칙

다섯 선지는 다음 조건을 모두 만족해야 한다.

1. 정확히 한 선지만 대상 용어에 맞는다.
2. 각 오답은 그 출처 개념에 대해서는 사실인 문장이어야 한다.
3. 다섯 선지는 모두 같은 문제 유형의 설명이어야 한다.
4. 정답과 오답의 길이, 문체, 구체성 수준을 비슷하게 맞춘다.
5. 대상 용어와 그 별칭을 선지에 반복하지 않는다.
6. 각 선지의 출처 용어명이나 요소 코드를 선지 안에 노출하지 않는다.
7. 두 선지가 대상 용어에 동시에 적용될 수 있는 경우 문항을 차단한다.
8. 부정문, 이중부정, `항상`, `절대` 같은 과도한 단정은 근거가 있을 때만 사용한다.
9. `옳지 않은 것`을 찾는 역문항은 초기 v2에서 만들지 않는다.
10. 선택지 순서는 문항 ID와 seed로 결정론적으로 섞는다.

정답 제출 후 표시되는 해설은 대상 용어명을 밝혀도 된다. 다만 관계형 해설도 우선 자연어로 설명하며, 공식 학습이 필요하면 별도의 수식 카드로 연결한다.

## 6. 좋은 문항과 잘못된 문항

### 좋은 예시: 정의형

```text
다음 중 ‘계속가치’를 가장 정확하게 정의한 것은?

A. 명시적으로 예측한 기간 이후의 현금흐름을 예측 종료 시점의 한 금액으로 요약한 가치다. [정답]
B. 채권자와 주주가 요구하는 수익률을 자금조달 비중에 따라 합친 값이다.
C. 영업활동에 투입한 자본으로 얼마의 세후 영업이익을 냈는지 보여 주는 지표다.
D. 판매를 위해 현금을 지출한 뒤 고객에게 회수하기까지 걸리는 순기간이다.
E. 비교기업의 거래가격을 목표기업의 실적 지표에 적용해 산출한 가치다.
```

### 좋은 예시: 관계형

```text
다음 중 ‘채권 듀레이션’의 핵심 관계를 올바르게 설명한 것은?

A. 만기가 길고 중간에 받는 현금흐름이 작을수록 금리 변화에 대한 가격 민감도가 커지는 경향이 있다. [정답]
B. 재고 보유기간이 길수록 영업에 묶이는 현금의 기간은 짧아진다.
C. 요구수익률이 높아질수록 같은 미래 현금흐름의 현재가치는 커진다.
D. 부채 비중이 커질수록 주주의 잔여 위험은 항상 작아진다.
E. 손실 가능성이 커질수록 신용위험에 요구되는 추가 보상은 작아진다.
```

### 잘못된 예시

```text
다음 설명에 맞는 용어는?
자산 = 부채 + 자본

A. 회계등식
B. WACC
C. ROIC
D. 현금전환주기
E. 듀레이션
```

잘못된 이유는 문제 방향이 반대이고, 수식이 그대로 노출되며, 용어만 나열된 선지가 설명 이해도를 측정하지 못하기 때문이다.

## 7. 데이터 계약

### 7.1 사실 레코드

```json
{
  "factId": "CF-07:verbal_relation:01",
  "elementId": "CF-07",
  "factType": "verbal_relation",
  "text": "각 자금조달 원천의 요구수익률이 높아질수록 전체 자본비용도 높아지며, 시장가치 비중이 큰 원천의 영향이 더 크다.",
  "sourceIds": ["..."],
  "sourceLocator": "...",
  "reviewStatus": "reviewed",
  "contentSha256": "..."
}
```

릴리스 문항에 사용할 수 있는 `factType`은 다음과 같다.

- `definition`
- `intuition`
- `verbal_relation`

기존 `core_relation`은 근거 자료로 보존할 수 있지만, 수식이 포함된 원문을 선지 텍스트로 직접 사용할 수 없다.

### 7.2 문항 레코드

```json
{
  "questionId": "CF-07-term_to_verbal_relation-01",
  "elementId": "CF-07",
  "questionType": "term_to_verbal_relation",
  "stem": "다음 중 ‘WACC’를 가장 정확하게 설명한 것은?",
  "choices": [
    {
      "key": "A",
      "elementId": "CF-07",
      "factId": "CF-07:verbal_relation:01",
      "text": "각 자금조달 원천의 요구수익률이 높아질수록 전체 자본비용도 높아지며, 시장가치 비중이 큰 원천의 영향이 더 크다.",
      "isCorrect": true
    }
  ],
  "sourceFactIds": ["CF-07:verbal_relation:01"],
  "split": "train"
}
```

`elementId`와 `factId`는 내부 추적용이다. 앱은 `stem`과 `choices[].text`만 채점 전에 표시한다.

## 8. 오답 후보 생성

오답 단위는 더 이상 다른 개념의 **용어명**이 아니라 다른 개념의 **같은 유형 설명 사실**이다.

예를 들어 `term_to_verbal_relation` 문항에는 다른 요소의 `verbal_relation`만 후보로 넣는다. 정의, 직관, 관계 설명을 한 문항 안에서 섞지 않는다.

후보 생성 순서는 다음과 같다.

1. 대상 요소와 동일한 요소의 다른 문장을 오답에서 제외한다.
2. 검토 완료 상태가 아닌 사실을 제외한다.
3. 대상 용어 또는 선택지 출처 용어가 문장에 직접 드러나는 사실을 제외한다.
4. 수식·LaTeX·요소 코드·내부 식별자가 포함된 문장을 제외한다.
5. 정규화 후 같은 뜻이거나 거의 같은 문장을 제외한다.
6. 문장 유형, 길이, 문체가 지나치게 다른 후보를 제외한다.
7. 남은 후보 중 같은 도메인과 인접 도메인의 혼동 가능성이 높은 설명을 랭킹한다.

좋은 오답은 대상 용어에는 틀리지만 출처 개념에는 정확해야 한다. 사실 오류를 섞어 어렵게 만드는 방식은 사용하지 않는다.

## 9. 모델링 목표

모델은 금융 설명을 새로 창작하지 않는다. 검토된 설명 사실 중에서 대상 용어와 혼동하기 좋은 오답 네 개를 고르는 순위 모델이다.

v2의 랭킹 입력은 다음과 같다.

- 대상 표현: 용어명, 별칭, 도메인, 검토된 정의·직관·관계 사실
- 후보 표현: 같은 문제 유형의 검토된 설명문과 그 출처 요소 메타데이터
- 출력: 후보 설명의 오답 적합도 순위

초기 feature는 다음을 비교한다.

- 대상 개념 표현과 후보 설명의 word/char TF-IDF 유사도
- 대상 개념 사실과 후보 사실의 의미 유사도
- 동일·인접 도메인 여부
- 정의·직관·관계 유형 일치 여부
- 길이와 문체 균형
- 숫자·수식·약어 형태 차이
- 용어명·별칭 누출 여부
- 사람 검토 오답 적합도

v1의 설명 질의와 용어 후보로 계산한 학습 결과, 지표, 사람 승인, 문항 수정은 v2 라벨로 재사용하지 않는다.

## 10. 데이터 분할과 실험

- 분할 단위는 행이 아니라 `elementId`다.
- 같은 요소의 정의·직관·관계 문항은 같은 split에 둔다.
- train, validation, test 사이에 대상 요소와 파생 문장이 겹치지 않아야 한다.
- 모델과 feature 선택은 train과 validation만 사용한다.
- test는 구성을 고정한 뒤 한 번만 평가한다.
- v2 첫 실행은 `bootstrap_not_reviewed`에서 시작한다.
- v1 실험과 직접 점수 비교하지 않고 새 기준선을 만든다.
- 새 실험 ID에는 v2 계약 버전을 포함한다.

## 11. 자동 품질 검사

모든 문항에 다음 검사를 적용한다.

- 문제 방향이 `term_to_*`인지 확인
- 다섯 선지가 모두 설명문인지 확인
- 정확히 한 선지만 대상 요소를 가리키는지 확인
- 같은 문제 유형의 사실만 사용했는지 확인
- 대상 용어와 별칭이 선지에 누출되지 않았는지 확인
- 선지 출처 용어명과 요소 코드가 노출되지 않았는지 확인
- 관계형 선지에 수식 또는 LaTeX가 없는지 확인
- 중복·유사 정답·사실 오류가 없는지 확인
- 정답 선지만 길이·구체성이 튀지 않는지 확인
- 모든 정답과 오답 사실에 검토된 출처가 있는지 확인
- 동일 입력과 seed에서 문항은행 해시가 재현되는지 확인

자동 차단 문항은 Owner가 승인으로 덮을 수 없다. 사실 또는 선지를 수정하고 다시 생성해야 한다.

## 12. 사람 검수와 릴리스 게이트

v2 문항은 새 fingerprint와 새 `reviewInputSha256`을 사용한다. v1의 승인·반려·수정·배치 승인은 전부 무효다.

릴리스 전 최소 조건은 다음과 같다.

| 게이트 | 기준 |
|---|---:|
| 문제 방향 위반 | 0건 |
| 선택지 5개·정답 1개 위반 | 0건 |
| 용어명·별칭·코드 누출 | 0건 |
| 관계형 수식 노출 | 0건 |
| 중복 또는 복수 정답 | 0건 |
| 출처 누락 | 0건 |
| test 요소 사람 라벨 커버리지 | 100% |
| 자동 차단 | 0건 |
| 미확인 Owner 예외 | 0건 |
| 현재 검수 입력의 Owner 배치 승인 | 필수 |
| 동일 입력 재빌드 SHA-256 | 일치 |

약지도 점수가 높아도 독립 사람 검수와 배치 승인이 없으면 `release_ready`가 될 수 없다.

## 13. Admin 표시 원칙

Admin 모델 화면에는 v2 실험만 표시한다.

- 재설계 후 첫 실험 전에는 `실험 없음 · 새 기준 준비 중` 상태를 표시한다.
- 폐기된 v1 실험, 문항, 승인, 수정 이력은 현재 지표나 검수 큐에 섞지 않는다.
- 각 실행에는 계약 버전, 데이터 해시, 모델 구성, validation/test 결과, 자동 차단, Owner 상태를 기록한다.
- 정적 실험 보고서와 Supabase 검수 데이터의 fingerprint가 일치하는 경우만 결정을 반영한다.
- `candidate`와 `bootstrap_not_reviewed`는 APK 릴리스 대상으로 표시하지 않는다.

## 14. 앱용 SQLite

앱에는 모델 바이너리가 아니라 검증된 문항과 설명 선지만 넣는다.

`concept_questions`에는 대상 용어를 포함한 `stem`을 저장하고, `concept_question_choices.text`에는 화면에 보일 설명문을 저장한다. 각 선택지의 `element_id`와 `fact_id`는 내부 검증과 해설 추적에만 사용한다.

Android는 다음을 지켜야 한다.

- 긴 설명형 선지가 잘리지 않고 여러 줄로 표시된다.
- 선택지 높이는 내용에 따라 늘어난다.
- 요소 코드와 출처 개념명은 채점 전에 숨긴다.
- 선택 후 정답 해설과 오답이 가리킨 개념을 별도 영역에서 설명할 수 있다.
- 문항은행이 `release_ready`가 아니면 release APK 생성과 게시를 차단한다.

## 15. 초기화 범위

v2 시작 시 다음 v1 산출물은 폐기한다.

- Admin 개념형 모델 실험 JSON과 Markdown 실험 보고서
- v1 문항은행과 fingerprint
- Owner 문항 승인·반려 및 배치 승인 기록
- Admin에서 저장한 v1 문항 수정 기록
- v1 랭커 모델, 임베딩 캐시, 후보·사실 build 산출물
- v1 지표와 릴리스 게이트 상태

다음 원본은 보존한다.

- 검토된 135개 금융 요소와 출처
- 정의·직관·핵심 관계의 원본 콘텐츠
- 일반 콘텐츠 DB와 용어집 데이터
- 모델링 파이프라인 코드의 재사용 가능한 인프라

보존된 원본도 v2 설명 선지로 사용하기 전에는 새 계약 검사를 통과해야 한다.

## 16. 구현 순서

1. 이 문서를 v2 단일 기준으로 확정한다.
2. Admin v1 실험·검수 데이터를 초기화한다.
3. `verbal_relation` 사실 스키마와 작성·검수 규칙을 구현한다.
4. 문항 생성 방향을 `term_to_*`로 전환한다.
5. 설명 선지용 후보 생성과 오답 랭커를 다시 학습한다.
6. 수식·용어명 누출·복수 정답·문체 불균형 검사를 추가한다.
7. Admin에서 긴 설명 선지를 수정·검수할 수 있게 한다.
8. Android를 설명형 선지 레이아웃과 새 문항 계약에 맞춘다.
9. v2 bootstrap, validation, 고정 test, Owner 검수를 순서대로 수행한다.
10. 모든 게이트가 `release_ready`일 때만 APK를 빌드·게시한다.

## 17. 완료 정의

다음 조건을 모두 만족해야 v2 모델링이 완료된 것으로 본다.

- 모든 문항이 용어를 문제로, 설명을 선지로 사용한다.
- 관계형 문항의 선지가 수식 없이 방향과 조건을 자연어로 설명한다.
- 정답과 오답이 모두 검토된 사실과 출처에 연결된다.
- 모델은 설명을 창작하지 않고 검토된 오답 설명의 순위만 정한다.
- 독립 test와 자동 품질 검사를 통과한다.
- Owner 예외 검수와 현재 배치 승인이 끝난다.
- 동일 입력에서 문항은행과 SQLite 해시가 재현된다.
- Admin과 Android가 동일한 문항 계약을 표시한다.
- 릴리스 manifest가 `release_ready`다.
